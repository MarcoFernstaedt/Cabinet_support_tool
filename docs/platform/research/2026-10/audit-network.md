# Cabinet network, sync, firewall-policy and rollback audit

Read-only code audit of `/home/marco/cabinet_support_tool`. Findings are code-path assessments, not a Windows-cabinet execution test. Paths below are relative to that repository. `server/src/services/rules.ts` concerns **symptom/alert rules**, not Windows Firewall rules; firewall policy and bulk execution live in `server/src/services/firewall-policy.ts` and `fleet-jobs.ts`. The older specification is not always authoritative: `docs/spec/04-agent-spec.md:126-128` omits `firewall.applyPolicy`, but `agent/src/Cabinet.Agent.Core/Writes/BrokerWrites.cs:153-185` and `contracts/schemas/operations/catalog.json:24-29` explicitly arm its safety net.

## Scope and actual recovery boundary

The broker's two-minute window (`agent/src/Cabinet.Agent.Core/Writes/SafetyNet.cs:16,58-70`) covers **six operations per cabinet**: `network.setIp` (`BrokerWrites.cs:32-53`), `network.setDns` (`:98-108`), `firewall.setProfile` (`:130-149`), `firewall.applyPolicy` (`:153-185`), `firewall.setRule` (`:190-227`) and `firewall.restore` (`:231-243`). `firewall.applyPolicy` is not a gap in coverage *on an individual cabinet*: it snapshots the full firewall, changes profiles, and arms one timer. The bulk policy API enqueues that operation separately for each selected cabinet (`server/src/services/firewall-policy.ts:142-173`); fleet jobs can enqueue it in batches (`server/src/services/fleet-jobs.ts:210-249`). There is **no two-minute transaction or rollback across the site**. Server-side `setClientPolicy`/`setFleetPolicy` only update desired policy and evaluate drift (`firewall-policy.ts:103-123`), not the machines; a later apply is needed.

Outside this net: `network.renewLease` can release a working DHCP lease before renewal and is explicitly unprotected (`BrokerWrites.cs:57-84`); `network.flushDns` changes only resolver cache (`:87-92`); `service.setStartType`, `service.control`, `updates.uninstall`, installs and other writes have `safetyNet: false` (`agent/src/Cabinet.Agent.Contracts/Catalog.cs:121-132`). The platform reads hosts (`docs/spec/04-agent-spec.md:77`; `agent/src/Cabinet.Agent.Windows/HardwareOperations.cs:182-205`) and WinHTTP proxy (`agent/src/Cabinet.Agent.Windows/NetworkExtras.cs:109`), but has no hosts/proxy write in the compiled write catalog (`Catalog.cs:115-132`). A Windows Update *policy* write and scheduled-task mutation are not implemented here (`docs/spec/09-open-decisions.md:456`; `server/src/services/config-ingest.ts:32-35`); `updates.uninstall` is distinct from editing Update policy. External Group Policy, administrator, software installer or other non-platform changes to DNS/hosts/proxy/firewall/services/tasks are not reverted by this broker safety net. **Hypothesis:** if one of these external or unprotected changes prevents the network process reaching the platform, polling/results/heartbeats cannot repair the connection automatically; only an applicable local watcher, an OS/external policy reversal, or hands-on access can. The broker's rollback loop runs on start-up and every five seconds for *pending covered entries only* (`agent/src/Cabinet.Agent.Broker/Program.cs:70-78`; `BrokerWrites.cs:258-297`). The service watcher tries to start watched services (`Program.cs:81-88`), but is not a general policy rollback. No guarantee of self-recovery follows from the agent being installed.

## Findings

1. **Critical — rollback failure is durably misreported as success and never retried.** `agent/src/Cabinet.Agent.Core/Writes/SafetyNet.cs:112-125`: `catch (Exception ex) { ... log(...) } ... s.Pending.Remove(e); Record(s, e.CommandId, SafetyNetState.RolledBack);`. If firewall import or network restoration fails while the cabinet is cut off, the pending recovery instruction is deleted and the command becomes `RolledBack`; even the broker restart cannot retry. `agent/src/Cabinet.Agent.Core/Server/AgentConnection.cs:743-752` also emits `safety_net_rollback` after a delay without consulting the broker. **Smallest fix:** retain failed entries on disk with an explicit rollback-failed state and retry them; only mark rolled back and send that result after successful restore *and* readback of the saved state. Surface failure independently to operators.

2. **High — two-phase write has an unprotected interval and some exceptions bypass partial-change arming.** `agent/src/Cabinet.Agent.Core/Writes/BrokerWrites.cs:103-108`: `network.SetDns(...); ... safetyNet.Arm(...)`; `:238-241`: `firewall.Import(...); store.Record(...); ... safetyNet.Arm(...)`. `SetDns` and `Restore` do not use `ArmIfPartlyApplied`, unlike IP/profile/rule/policy; all six arm **after** mutation, and `ArmIfPartlyApplied` at `:117-125` catches an arm failure only to log and rethrow. A partial WMI DNS write, partial firewall import, process kill/reboot between change and arm, or state-file save failure can leave a broken network/firewall without a pending durable rollback. The server does have the previously queued command and issue audit (`server/src/services/firewall-policy.ts:164-171` and normal command issuance), so “no durable record” here means **no durable local undo instruction/after-state**, not necessarily no server audit row. **Smallest fix:** durably persist the before-state and pending rollback *before* any mutating call, including imports, then read back the after-state and settle or retry the rollback on failure/cancellation.

3. **High — IPv4 rollback does not faithfully restore a no-gateway state.** `agent/src/Cabinet.Agent.Windows/NetworkControl.cs:101-108`: `if (ip.Gateways.Count > 0) Invoke(a, "SetGateways", ...)`; there is no empty-gateway branch in `Restore`. By contrast `SetStatic` explicitly attempts to clear a previous gateway when the new setting has none (`:69-76`), but **swallows** failure (`catch ... { }`). If a covered IP change adds a gateway to a previously routerless adapter and loses server contact, rollback restores IP/DNS yet may leave that gateway, changing routes and potentially retaining the outage. **Smallest fix:** make restore clear gateways when the saved list is empty, fail visibly if Windows refuses, and compare IPv4 address/mask/gateway/DNS to the snapshot before confirming rollback.

4. **High — mere server response can keep a bad covered change, including a rejected result.** `agent/src/Cabinet.Agent.Core/Server/AgentConnection.cs:715-735`: on HTTP `BadRequest`, `NotFound` or `Conflict`, `reached = true; // the server answered`, followed by `s.Outbox.Delivered(...)` and `ConfirmSafetyNet`; `agent/src/Cabinet.Agent.Core/Writes/SafetyNet.cs:74-85`: `Confirm` marks `Kept` without checking the deadline itself. Thus a changed firewall/DNS can remain even though its result was refused and no successful result is stored server-side; an unrelated connectivity response proves only that *some* server endpoint answered, not a healthy future poll. **Smallest fix:** confirm only an accepted, authenticated result for this command (or a verified idempotent duplicate), require `now < deadline` in broker confirmation, and preserve/report refusal as an unsettled result rather than mark the outbox delivered.

5. **High — blanket policy application can cut off a sync cabinet and strand satellites before its own rollback.** `server/src/services/firewall-policy.ts:19,125-134,142-173`: `DEFAULT_POLICY = { domain: "off", private: "off", public: "off" }`, targets are online writable cabinets that differ, with no sync-role/dependency ordering; `server/src/services/fleet-jobs.ts:68-78,99-103,210-249` similarly plans and issues batches without a sync-role guard. Each cabinet can still roll back *its own* change if it cannot contact the platform, but blocking satellite-to-sync traffic does not necessarily block **the sync cabinet's outbound platform connection**, so that change can be confirmed and kept while satellites lose their application sync. **Hypothesis:** the precise outage depends on local firewall rules and sync traffic. **Smallest fix:** preflight and order/exclude the site's sync cabinet in disruptive policy batches, verify dependent satellite-to-sync connectivity before declaring the operation safe; do not infer satellite health from sync cabinet→platform confirmation alone. This is a safety fix to existing bulk application, not a proposal for an unrelated feature.

6. **High — bulk changes are not all-or-nothing and cancellation cannot undo issued writes.** `server/src/services/firewall-policy.ts:164-173`: one transaction inserts up to 200 **queued commands** and replies with IDs, not applied results. `server/src/services/fleet-jobs.ts:189-199,237-249`: batches are issued later; `:357-371`: `Cabinets not yet reached are cancelled now; a batch already sent finishes`. Some targets can be verified, failed, offline, unverified or cancelled while others retain changes; job-level `done`/`cancelled` is not a uniform applied outcome. `:259-297,377-401` stores per-target states/counts, and `server/src/console-api/firewall-routes.ts:50-54` returns 202 rather than completion. **Smallest fix:** never present a queued bulk as success; report per-cabinet final state and aggregate partial/failed explicitly (including on cancellation), and require a deliberate compensating per-cabinet rollback where a uniform outcome is operationally required. No current all-or-nothing guarantee can be claimed.

7. **Medium — `network.trace` accepts a browser-supplied LAN target unlike `network.test`.** `server/src/services/console-commands.ts:53-63`: only `if (operation === "network.test")` strips and server-fills `syncAddress`; `agent/src/Cabinet.Agent.Core/CommandValidator.cs:137-146`: trace checks only whether supplied address is private and on a local /16-or-narrower network; `NetworkTester.cs:251-264` actually probes it, and `:268-300` returns hop/reached/timing. An authenticated Tier 1 console user (or compromised server) can issue `network.trace` with `target=sync_cabinet` and vary `syncAddress` among LAN hosts (not arbitrary Internet hosts), obtaining an ICMP reachability oracle at 12 traces/minute per cabinet (`RateLimiter.cs:15-21`, `CommandValidator.cs:117-123`). **Smallest fix:** strip/fill trace `syncAddress` from the same site setting as tests, and have the agent enforce a locally pinned approved target or restrict this operation further if the threat model includes a compromised server. The present local-subnet check alone is not a peer identity check.

8. **Medium — local fallback sync and platform names can resolve beyond the IP guard.** `NetworkTester.cs:60-67,104-112,251-264,303-315`: server-provided sync IP is locally validated, but absent `syncAddress` falls back to `_config.SyncCabinet.Address`, which may be a name, and both that name and `_config.PlatformServer.Host` resolve via the system resolver; the code uses the first address for ping/TCP and returns up to 16 resolved IPs. `CommandValidator.cs:145-152` validates only a **supplied** sync IP and allows configured TCP ports across target kinds. There is no fresh destination-IP verification after DNS resolution; a malicious or stale DNS/hosts answer can redirect a bounded-name test to an unintended destination (and a locally configured sync name has no same-subnet check). This is **not** a free-form browser TCP scanner: local configured ports, four target kinds, and rate limits still apply. **Smallest fix:** restrict sync fallback to validated local private IPv4 and revalidate resolved destination before connection; pin platform tests to the configured server endpoint/expected port or explicitly constrain resolved addresses to an approved destination set. State that Windows resolver caching may make DNS test results differ from live DNS rather than claiming an application cache exists.

9. **Medium — authorized network-test probing has a broader surface than the old prose says.** `contracts/schemas/operations/network.test.schema.json:15-60,73-81`: four target kinds, `dnsServerIndex` 0–3, sync address/ports max four, 20 ping samples or 10 TCP samples; `CommandValidator.cs:147-152` allows **any** port in local `AllowedTcpPorts` for gateway, DNS, sync or platform, plus up to four site-configured ports for sync. `RateLimiter.cs:15-21,24-45` enforces 10 test **commands**/minute in memory, not 10 packets/minute or durable across restart; `NetworkTester.cs:133-152,156-211` distinguishes connected, refused and timeout and returns timing. The console replaces browser-provided sync address/ports (`console-commands.ts:53-62`) and admin sync settings require step-up (`server/src/services/settings.ts:52-60`, `device-settings.ts:89-106`), so a normal Tier 1 user cannot choose arbitrary sync IP/port through `network.test`. **Hypothesis:** a malicious Admin changing the site sync IP/ports, or a compromised command issuer, could enumerate hosts on an attached private subnet and four configured ports at this bounded pace; current controls mitigate, but do not prove “cannot scan.” **Smallest fix:** bind server-provided sync IP to an enrolled same-site sync cabinet's reported address (not merely an arbitrary same-subnet private IP), apply a durable per-cabinet probe/packet budget, and limit TCP ports by target service rather than sharing the entire local list across targets.

10. **Medium — packet-loss diagnosis exists, but cannot establish the cause of a past sync outage.** `NetworkTester.cs:156-224` implements ICMP echo series and TCP connect series with sent/received, loss percentage, min/avg/max and jitter. `server/src/diagnose/network.ts:83-97` requests four gateway pings, ten sync pings and five connects per configured sync port **on demand**, but only a DNS lookup to the platform (`:89`) and a trace (`:96`). A single diagnosis after an outage can show current path loss, not establish packet loss during the lost-sync interval or separate ICMP filtering from failed application TCP/TLS. `server/src/diagnose/network-findings.ts:202-238` already distinguishes no ping answer from working sync ports. **Smallest measurement addition required:** add a bounded, low-bandwidth periodic sample from each satellite to the *approved same-site sync endpoint* and platform endpoint: a short ICMP echo series where permitted (no elevation required for .NET `Ping` in the deployed network service subject to Windows policy), paired with TCP connect attempts to the known sync port and the actual platform HTTPS port (unprivileged sockets), storing timestamp, endpoint, attempts, successes/timeouts/refusals and RTT distribution. Treat ICMP silence as inconclusive when TCP succeeds; TCP-connect failure ratio is not proof of IP packet loss. Correlate sample windows with heartbeat/sync failures. Reuse the four target kinds, authenticated site binding, fixed service ports, per-cabinet cadence/budgets and no arbitrary host/port fields; do not run privileged packet capture or a general ICMP scanner. This is the only measurement addition recommended here.

11. **Medium — DHCP release/renew may sever the only connection without recovery.** `BrokerWrites.cs:66-82`: `if (p.Release == true) network.ReleaseLease(...); int code = network.RenewLease(...)` with just three more three-second retries. `Catalog.cs:128` marks `network.renewLease` safety-net false because it changes no configured setting, but the current DHCP lease/address can disappear; if the server is lost, a queued failure result cannot restore the lease, and the old address may be unavailable even to a retry. **Smallest fix:** do not release a working lease merely to renew in routine use; treat explicit release as a disruptive exception with on-box bounded retry/recovery and a clear warning that restoring the original lease is not guaranteed.

12. **Low — firewall snapshot/change history is not a durable record of every partial mutation.** `BrokerWrites.cs:136-145,164-182,211-226,238-241` records the firewall fingerprint *after* mutations, not inside the exception path. `agent/src/Cabinet.Agent.Core/Monitoring/FirewallWatch.cs:46-55` saves the first observed hash as baseline without emitting an event; `:65-83` labels a matching journal hash as platform-caused. A half-import or half-profile update followed by loss/reboot may leave a snapshot and server-issued command, but not a journal after-state; if the watcher first starts afterward it emits nothing. **Smallest fix:** keep a durable pre-mutation intent/rollback outcome journal and emit a distinct failed/partial mutation event once service reconnects; do not rely on periodic firewall fingerprinting as the rollback record.

## Verification limits

No Windows cabinet, platform database or running API was touched. Severity reflects reachable failure paths in source, not an observed field incident. The default policy intentionally turns firewall profiles off (`firewall-policy.ts:19`); whether that helps or harms a particular site depends on its actual rules and topology. Existing telemetry mode is server-directed heartbeat pacing (`agent/src/Cabinet.Agent.Core/Server/Connectivity.cs:264-325`), not evidence of a periodic sync-path loss history. This audit makes no proposal to build hosts/proxy/Update-policy/task writes, nor asserts that such writes currently exist.
