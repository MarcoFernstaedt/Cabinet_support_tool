# USB hardware and dependent-workload monitoring design

**Scope:** Windows 10/11 cabinet agent; design/research only. No repository changes. This is an implementation proposal, not a claim of Windows fleet validation. Numeric policy values below are proposed defaults, not Windows guarantees. Citations refer to the URL list generated below; repository references are exact paths/lines in the inspected checkout.

## Executive decision

Use **CM_Register_Notification as a low-latency invalidation signal plus a persisted, periodically reconciled PnP snapshot**; neither callbacks nor event logs alone are a durable inventory. Register before the first enumeration, queue callback data without blocking, then enumerate, deduplicate and reconcile; Windows explicitly documents the register-then-enumerate race and double observation.[1] Use the physical devnode tree and location paths for topology, device identity only when backed by a credible serial/unique identifier, and explicit application-specific probes for attachment. Event logs are **diagnostic corroboration**, not the primary reconnect counter. Auto-remediation of drivers, hubs, arbitrary services and applications is out of scope.

## Existing integration points and gaps

- `Monitoring/MonitorHost.cs:27-39,82-131,161-169`: 60-second scanner polling through `MonitorSources.Devices`; no general USB monitor. Add `UsbTopology` source (broker or carefully permissioned reader), `UsbHealth` source for declared workload probes, event-driven reconciliation queue, and a bounded periodic sweep. Preserve optional-source behavior and read-only monitor/privileged broker boundary (`MonitorHost.cs:42-46`).
- `Monitoring/ScannerWatch.cs:12-59`: only fingerprint scanner; its previous state is in memory, first unconfigured/unseen scanner stays quiet; no durable absence timer. Reuse its classification as a scanner-specific view, but do not infer all USB disappearances from its `null` result.
- `Monitoring/EventLogWatch.cs:57-99,104-129`: two-minute query, five pages × 100, record bookmark and flood summary; this may omit older records in an overflow, and Error/Warning/Critical filtering excludes informational starts (410). Do **not** count its emitted `AgentEvent`s as reconnections. Create a separate narrow PnP evidence reader with its own cursor, retaining overflow/clear uncertainty rather than silently setting a count.
- `Monitoring/MonitorSettings.cs:19-60`: persisted heartbeat response currently carries scanner IDs and watched service names; extend contract/schema and persistence with *validated, versioned, bounded* USB policy. Do not let server-delivered data become a generic executable process/service operation. Existing watched-service loop (`MonitorHost.cs:112-115,134-150`) reports broker status; that is not proof a service has opened the peripheral.
- `Helpers/UsbLocation.cs:9-25` parses just one `Hub_#...` / `Port_#...` pair from display location text; `KindOf` (`:27-30`) guesses from name and USB class. Extend collector with true location-path list, parent chain, interface GUIDs and container IDs; never use the parsed hub number alone as a fleet-stable key. `Helpers/ScannerChecklist.cs:43,159-165` uses fixed `>3` scanner reconnects in 24 h inferred from starts; keep as legacy presentation until replaced with configurable confirmed transition counts. `Helpers/DeviceProblems.cs:10-35` maps problem codes; distinguish code 21 removal in progress, 24 uncertain, 28 no driver, 43 reported failure, 45 disconnected, 47 prepared for removal, and 52 signature failure. Windows exposes `Present`, `PNPDeviceID`, `Service` and `ConfigManagerErrorCode` via Win32_PnPEntity.[7]
- `docs/spec/04-agent-spec.md:50-62,64-75,141-147` permits System, Kernel-PnP/Configuration and DriverFrameworks-UserMode/Operational; `devices.list`, `usb.ports` and `peripheral.status` are read-only views. `usb.ports` deliberately excludes `MI_` interfaces and includes remembered nonpresent devices, but its registry `Port_#0002.Hub_#0003` cannot alone establish the *current* occupant. Add a physically present topology snapshot and separate historical last-seen slot. Do not expand allowed channels or enable disabled channels by server policy alone; a signed agent upgrade/local authorization is required by spec.

| Source / availability | What to implement | Important limitation |
|---|---|---|
| `WM_DEVICECHANGE`, `DBT_DEVNODES_CHANGED` (XP+, thus 10/11) | A window/message pump can receive a generic changed-devnodes hint, then rescan. `lParam=0`: **no device identity**.[4] | Session/window lifetime and no replay; do not host a hidden interactive-session window solely for a service when CM callbacks suffice. Many changes can collapse into one snapshot; cannot count exact physical cycles. |
| `RegisterDeviceNotification` (legacy device-notification API, 10/11) | Register for relevant **device interface class GUIDs**, receiving `DBT_DEVICEARRIVAL`, `DBT_DEVICEREMOVECOMPLETE` etc. at window **or service control handler**; distinguish interface GUID from device setup class GUID.[5][26] | Class-limited and subscriber-lifetime-bound; a multifunction USB physical device may expose several interface notices. Not a generic list of every USB physical devnode; no replay when service is down. |
| **SetupAPI / ConfigMgr** (10/11) | SetupDiGetClassDevs + SetupDiEnumDeviceInfo / SetupDiGetDeviceProperty or CM_Get_DevNode_Property for a **snapshot**, including nonpresent historical nodes only when explicitly requested; notification is via RegisterDeviceNotification or CM_Register_Notification, not an alleged `SetupDi...` subscription.[8][12][1] | Snapshot misses a disconnect/reconnect between sweeps; nonpresent registry nodes are history, not live attachment. |
| `CM_Register_Notification` (Windows 8+, thus 10/11) | In a service, register `CM_NOTIFY_FILTER_TYPE_DEVICEINSTANCE` with `CM_NOTIFY_FILTER_FLAG_ALL_DEVICE_INSTANCES` and empty instance ID for broad devnode changes, and/or targeted device-interface GUIDs; handle `DEVICEINSTANCEENUMERATED/STARTED/REMOVED`, `DEVICEINTERFACEARRIVAL/REMOVAL`, and handle-specific query-remove/complete where relevant. Copy identifiers promptly, dispatch asynchronously, `CM_Unregister_Notification` at shutdown.[1][2][3] | Callback registration is not persistent and does not enumerate interfaces already present. Register then enumerate; a race can produce both callback and snapshot. Callback must be quick; a down/crashed service has a gap, filled only by reconciliation or retained log evidence.[1] |
| WMI `Win32_DeviceChangeEvent` (Vista+, 10/11) | Optional generic hint: `SELECT * FROM Win32_DeviceChangeEvent`; `EventType` 1 configuration, 2 arrival, 3 removal, 4 docking; then snapshot.[6] | No device ID in its declared fields; docking and mapped-device changes may appear; WMI availability/permissions and consumer lifetime vary. `Win32_PnPEntity` is a **state query**, not a precise USB interrupt. `__Instance*Event WITHIN n` instead polls snapshots and may miss transients and cost CPU.[6][7][17] |
| Windows Event Log (10/11) | On allowed `Microsoft-Windows-Kernel-PnP/Configuration`, inspect candidate **400 configured, 410 started, 411 start problem, 420 deleted**; System Kernel-PnP **219 failed driver load**; `DriverFrameworks-UserMode/Operational` candidate **2003, 2100/2102** lifecycle and System **10110/10111/10114** UMDF host/device failures. Query provider + channel + ID + **event XML fields**, not ID alone; correlate to instance and current status.[19][20] | Candidate ID-to-meaning mapping varies by provider/channel/build and UMDF type; **410 is a start, not a proved unplug/replug**. 2003 can represent UMDF host shutdown (not universal USB arrival); 2100 may occur in both connect/eject sequences. Operational UMDF channel can be disabled; logs roll over, clear, or have permission errors. 219 can be transient: Microsoft documents a WUDFRd load warning with concurrent UMDF 10114.[19][20] |

**Event-log detail:** the NXLog USB audit reference lists Kernel-PnP 400/410/430 on first connection and multiple UMDF IDs for connection/ejection, **not** a universal 410-per-USB-reconnection guarantee.[19] Before enabling an event-ID-derived heuristic, capture `Get-WinEvent -ListLog`, `wevtutil gp Microsoft-Windows-Kernel-PnP /ge:true` / `wevtutil gp Microsoft-Windows-DriverFrameworks-UserMode /ge:true` and actual XML on representative Windows 10 and 11 cabinet builds; filter `Provider/@Name`, `Channel`, `EventID`, instance data, boot epoch and `EventRecordID`. Treat 411 or 219 as **driver failure evidence**, confirmed by current problem code and driver/service state; do not equate event alone with ongoing failure.[7][20]

**Durability:** save the reconciled snapshot, wall-clock timestamps, monotonic duration checkpoint, boot ID/epoch, policy version and event-log `(channel, record ID, time)` cursor atomically under ProgramData. On start/resume, register → enumerate → compare; if offline gap, log rollover/clear, `EvtSubscribeStrict` missing-record error or clock discontinuity, mark `eventHistoryIncomplete=true` rather than claiming zero reconnects. Windows Event Log supports persisted bookmarks and strict-subscription stale/missing-record indication; if keeping the existing bounded polling reader instead, report overflow separately.[15][16] After sleep/resume or boot, settle topology before evaluating absence; keep a separate source-health `unknown` state. Notify changes are hints, not a durable queue. These are design responses to documented subscription and callback lifetimes, not measured fleet loss rates.[1][15][16]

## 2. Identity, ports and moved-vs-gone

Persist separate **device** and **attachment** records: `cabinetId`, `usbPhysicalKey`, `identityConfidence`, `instanceId`, `containerId`, `vid/pid`, optional USB serial (protected/redacted or keyed hash), `parentInstanceId`, `locationPaths[]`, physical ancestor chain, interface paths/GUIDs, `lastPresentAt`, `lastSeenPort`, `bootEpoch`. `DEVPKEY_Device_LocationPaths` supplies a path through the device tree; `CM_Get_Parent` obtains parent devnode and `DEVPKEY_Device_ContainerId` groups multiple devnodes of one physical device.[8][21][9] Select the **physical USB parent** for policy, not each `USB\\VID_...&MI_...` function child; preserve each function's interface/driver status separately.[9]

`Port_#0002.Hub_#0003` from `SPDRP_LOCATION_INFORMATION` is display text and a local hub/port coordinate, not a globally unique permanent port ID. Define `portKey = cabinet + root-controller identity + normalized full DEVPKEY_Device_LocationPaths + current hub ancestor identities + downstream port chain`; keep the original text for technician display. A device moved to another socket changes path/port key; plugging a dock into another host port changes the path of **all descendants**; replacing a hub may change ancestor instance/identity and invalidate port-based assignment. This follows from location paths being tree-relative rather than a physical serial.[8][21]

A device instance ID is **system-supplied, locally unique**, not universally an immutable physical serial.[22] USB with valid unique serial can keep a device identity across ports; Windows can explicitly ignore USB hardware serial (`IgnoreHWSerNum`), tying an instance to a port instead.[11] Container ID can be vendor-supplied, a USB serial hash, randomly generated, or inherited from the parent for internal/nonremovable paths; therefore it is a grouping clue, not unconditional proof of the same physical unit across docks/reinstalls.[9][10] Never interpret a VID/PID match alone or a reused random/container ID as a proven move. Validate serial quality (nonempty, not all-zero/default, unique within cabinet); if unavailable, use `locationPaths + VID/PID + prior operator assignment` as a **slot expectation**, with low-confidence physical identity.[10][11]

**Move algorithm:** within a configurable 10-minute correlation interval, if the expected unit vanishes from A and a *unique, high-confidence* serial/vendor ContainerID appears at B, close A as `moved` and open B, retaining a `portVacant` warning if the policy requires that slot. If only VID/PID matches and two candidates exist, mark `ambiguous`, not moved. For a same-slot functional replacement, retire prior serial and require approved reassignment. When a dock/hub parent disappears, group descendant losses into one parent incident; if the parent returns at another root path and its distinct serial or operator-approved dock identity matches, report dock move plus dependent observations instead of N independent loss alerts. Registry nonpresent records are historical; compare them against **current present** nodes before making any move assertion.[7][8][9][10]

## 3. Dependency graph and actual attachment

Model typed, operator-approved edges: `physical USB → PnP function/interface → driver service → OS service or vendor application → functional probe`. `Win32_PnPEntity.Service` / `DEVPKEY_Device_Service` (`SPDRP_SERVICE`) returns the installed device driver service name; the INF's AddService sets it.[7][12] Query `Win32_SystemDriver` or SCM `OpenService(SERVICE_QUERY_CONFIG|SERVICE_QUERY_STATUS)` + `QueryServiceConfig`/`QueryServiceStatusEx(SC_STATUS_PROCESS_INFO)` for type, start type, current state and process ID **where meaningful**; a running shared/driver service does not prove this particular interface is bound or application-ready.[13][14] Check `CM_Get_DevNode_Status`/problem, present parent/children and the **correct enabled interface** before declaring driver health.[23][3]

Discover application links **from a signed local manifest** (approved service name, exact binary path/signature, interface GUID/expected interface path, permitted probes and restart capability) or an operator-pinned mapping; do not infer `service depends on USB` from a matching process name, process command line, SCM `DependOnService`, or device driver name. An app may use a COM port, HID, WinUSB, UMDF proxy or network service rather than an easily attributable raw USB handle. For attachment, prefer a vendor/standard non-destructive health call: app's own connection state for the *expected serial/interface*, open device interface in share-compatible **read-only** mode and query a harmless descriptor/status, or a declared pipe/API with response/freshness. `process running` and `SCM RUNNING` are only prerequisites. A handle can be evidence if an approved component exposes its handle or trace, but Windows supplies no universal stable `device → owner PID` inventory; enumerating every process's handles is intrusive, privilege-sensitive, race-prone and can miss indirect/mediated access. Do not deploy a generic handle-scraper as the primary attachment oracle. `Restart Manager` tracks resources to allow noncritical app restarts in installer scenarios, not a general USB interface dependency oracle.[24]

PnP orderly query-remove asks applications/drivers to release handles; open handles can cause a veto, while surprise removal bypasses orderly cooperation. `CM_Query_And_Remove_SubTree` is an **action** that prepares/removes a device and is not a safe observational probe; never call it to detect 'in use'. A pending/query-remove state is not the same as absent; label separately and allow settle time.[18][25][3] Do not restart USB controllers/hubs, disk/network/boot/security drivers, biometric driver stack, arbitrary vendor processes, shared `svchost`, the agent/broker, or an unknown service automatically. In this read-only design auto-restart defaults **off**. If a later product phase authorizes it: only exact allowlisted dedicated noncritical vendor **application service** with no child-dependency surprise, local write policy/role, maintenance gate, cooldown and bounded attempts; never let server rule text supply a service name to restart. The existing watched-services broker already has write behavior, so keep USB diagnosis separate from its restart path until explicit authorization is engineered and tested.

**Post-repair verification contract:** baseline the physical unit and interface path before action; wait through transition/settle; require (a) same expected high-confidence identity or approved replacement and present topology, (b) `CM_Get_DevNode_Status` started/no active problem and expected interface enumerated, (c) SCM service state as expected, and (d) application probe bound to the **new/current** interface or expected serial returning fresh success on two samples. If any fails, report `repairUnverified` with each layer's evidence and do not retry in a loop. A device being present, driver started, or service running alone is insufficient.[3][7][12][13][23]

## 4. Versioned policy contract: proposed defaults and bounds

Server returns only typed policy data; local schema validation rejects invalid or oversized sets and retains last valid policy on unreachable server. Resolve global → site → cabinet → exact pinned unit/slot; explicit `enabled`, `severity`, `scope`, schedule/timezone, `version` and effective timestamp, never inferred from absent fields. Suggested cap: 64 watched physical units, 16 rules/unit, 64 KiB payload; excess is validation failure. These are **product choices, unconfirmed operational thresholds** pending pilot, not Microsoft recommendations.

| Rule | Default | Allowed range / semantics |
|---|---|---|
| `absentFor` | 5 min, severity major for pinned critical scanner; off for unpinned unknown devices | 1–1440 min. Start after settled snapshot when an expected *device or slot* was known/configured, not when never-discovered automatic scanner is absent. Track cumulative continuous observed absence, persist first absent UTC and boot epoch; recovery clears only after 2 healthy samples separated by 30 s. |
| `reconnectCount` | 3 **completed present→absent→present cycles** in 60 min, minor | N=2–20, Y=5–1440 min; scope `device` (high-confidence serial only) or `port` (full port key). If uncertain identity, report count as lower bound or unknown. Do not count first enumeration, `410` alone, function-child duplicates, or boot/resume replay. |
| `quietHours` | none; notifications only, keep recording | Local site IANA zone, start/end minutes, weekdays, DST policy explicit. Critical safety/service-down still visible; defer *delivery* rather than reset timer/count. Server digest after period; allow per-rule override. |
| `severity` | minor reconnect, major sustained critical absence, informational move | enum informational/minor/major/critical, with critical restricted to approved business-impact mapping. Recovery inherits incident key rather than becoming a new independent page. |
| `settle/debounce` | 15 s after hint, 30 s after resume, 2 snapshots 10 s apart; max 120 s settle | debounce 2–60 s; resume 15–300 s; whole-parent storm grouping 5–120 s. A brief dropout remains in diagnostic counters if confirmed; no false 'continuous absence' from a single missing scan. |

Policy state machine: `unknown` (source unavailable / cold start) → `present` → `suspectAbsent` → `absent` after timer → `recovering` → `present`; `problem` is orthogonal (present with code/driver/probe failure). Persist transition ledger with boot epoch and durable journal; compare monotonic durations within a boot, UTC checkpoints across restart, clamp negative/implausible clock deltas and mark uncertainty. Slot policies continue warning if the same device moves away; device policies follow strong physical identity. Operator suppression/maintenance has expiry and reason; it cannot erase evidence.

## 5. Anti-flap and anti-storm at 8,000 cabinets

**Per agent:** callback writes to bounded channel (do not block PnP callback); coalesce hints over 2–15 s; one topology walk per burst, one periodic full sweep every 5 min with per-cabinet jitter, immediate post-resume/post-restart sweep; reconcile event-log evidence asynchronously. Keep exact per-key transitions in bounded ring/window and roll up aggregate counts, first/last timestamp, observed gaps and uncertainty. A hub/dock parent outage creates one parent incident plus a bounded affected-child list; child timers may continue for correctness but suppress duplicate paging. If channel overflow or reconciliation times out, expose `monitorDegraded` and rescan—never interpret missing telemetry as healthy. No unbounded queue or per-event WMI-wide scan.

**Server:** deterministic incident key `(cabinet, policy-rule, physical-or-port-key, parent-root-cause)`; deduplicate retries with immutable transition/event IDs. One open and one recovery per incident plus rate-limited updates (e.g. 15 min) and periodic 1 h digest; cap child fan-out (e.g. 20 exemplars + exact count), site-level correlate many cabinets on same dock/firmware or policy rollout without hiding per-cabinet state. Aggregate raw transitions locally; upload rollups at heartbeat and alerts on threshold, not every noisy function notification. Fleet budget example is intentionally a capacity target, not measured fact: 8,000 periodic 5-minute sweeps yield 1,600 average snapshots/minute across fleet, so use jitter and incremental payloads, never a synchronized start. Backpressure preserves critical incident summary before low-value raw evidence; report lost/overwritten evidence count.

**Pilot acceptance:** Windows 10/11 real hardware (serial and no-serial scanner, composite HID, USB serial, dock/hub cascade); physically unplug/replug quickly, move between ports/docks, swap identical units, suspend/resume, service restart and reboot, disable/enable UMDF channel, roll/clear log, driver failure, app running but detached. Record ground-truth physical actions and actual XML; validate no double count from MI functions/410, proper unknown on missed gap, one grouped dock incident, durable absence deadline and functional probe after an authorized repair. Linux .NET tests cannot validate Windows notification and SCM behavior.

## Failure modes / source interpretation

- Pure `DBT_DEVNODES_CHANGED`/WMI event: identity-free; possibly non-USB and no replay. Remedy: snapshot and persist.[4][6]
- Pure CM/SetupAPI callback: existing devices and downtime gap missing; registration/enumeration race duplicates. Remedy: register first, enumerate, dedupe; reconcile after downtime.[1]
- Pure periodic WMI/PnP snapshot: short cycles between sweeps invisible and nonpresent records mistaken for present. Remedy: transitions marked observed only, add callback/event evidence and `unknown` when insufficient.[7][17]
- Pure Kernel-PnP 410 reconnect count: initial start, driver restart, boot or dock enumeration masquerades as plug cycles; missing info-level events from existing watcher. Remedy: confirmed physical parent state transition count, event XML only corroborates.[19][20]
- UMDF event assumptions: channel may be off, IDs overlap lifecycle phases and can describe host shutdown rather than USB removal; kernel-mode devices may not use UMDF. Remedy: detect channel state, never universalize IDs.[19]
- Container/port identity: absent/bad serial, inherited/random ContainerID and moved hub path mean false merge or false disappearance. Remedy: confidence-tagged identity, full tree, operator-confirmed ambiguous moves.[8][9][10][11]
- Driver/service/app confusion: service running does not prove attached, process PID does not prove a current interface, query-removal is a disruptive action. Remedy: explicit manifest and functional probe; never automatic broad restart.[12][13][18][25]

## Unconfirmed / must validate on cabinet builds

1. Exact Kernel-PnP Configuration **420** removal wording and whether 430/other IDs are emitted for each monitored device on each Windows 10/11 build; no Microsoft normative per-USB-event-ID guarantee located. The NXLog table treats 400/410/430 as first connection, so do not treat 410 as ground truth.[19]
2. UMDF 2003/2100/2102 event semantics for specific scanner/dock drivers and channel default state on each OEM image; third-party source maps sequences rather than one-to-one USB arrival/removal.[19]
3. Whether a particular vendor's USB serial and ContainerID persist across ports/hubs, and whether duplicate serials exist; inspect real device descriptors and policy on hardware.[10][11]
4. Whether vendor service exposes an actual attachment/functional health probe and whether restart is safe; requires vendor documentation and a controlled Windows pilot.
5. Pilot-derived debounce, thresholds, throughput, and loss rates, including suspend/resume and log-overwrite behavior; all defaults here are engineering proposals, not empirically certified fleet values.
