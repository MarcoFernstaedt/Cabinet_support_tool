# Cabinet platform: adversarial server, console and data-path audit

Read-only source review; no database access, write-path exercise, deployment verification or live request testing. Evidence is source-level unless explicitly labeled hypothesis. The proposed `read version info from these file paths` and `data lite` features do not yet exist; their requirements below are design constraints, not claims of existing vulnerabilities.

## Findings

1. **High — concurrent release uploads share one temporary filename and can corrupt/replace the package.** `server/src/services/releases.ts:163-180`: `const temp = join(store.dir, ".incoming", `agent-${version}.zip`); ... createWriteStream(temp) ... await rename(temp, final)`. Two uploads for the same version open/truncate the same file; one can hash its own stream while the other's bytes land in that file, then rename a file whose contents do not match the digest it checked. This makes the database's `ready` state inconsistent with the artifact, and can deny or confuse an upgrade (the agent's final hash check remains the last safety barrier). **Fix:** use a unique, exclusive-created temp file per attempt; verify the completed on-disk file immediately before an atomic publish under a per-version lock; transition to `ready` only if the conditional update changed exactly one row.

2. **High — release package ownership is checked only before the upload, not on the mutation.** `server/src/console-api/upgrade-routes.ts:39-42`: `if (owner && owner.added_by !== u.userId) ...; return receiveReleasePackage(...)`; `server/src/services/releases.ts:159-161,181-184`: `SELECT state, sha256, size_bytes ... WHERE version = $1` and `UPDATE agent_releases SET state = 'ready' ... WHERE version = $1 AND state = 'awaiting_package'`. Another Admin can replace a refused release while the first request is streaming; the owner, manifest/hash and state can change between the authorization/read and publish. The service neither checks `added_by` nor checks its update row count. **Fix:** enforce `added_by = adminId`, expected hash/size and awaiting state in the same locked transaction as the final transition; serialize uploads by release/version, and discard the temp artifact if the compare-and-swap fails.

3. **High — full audit-chain verification does not detect a deleted suffix.** `server/src/db/db.ts:370-399`: `previous = ... "0".repeat(64)`; `SELECT TOP (...) ... FROM audit_log WHERE seq >= $1 ORDER BY seq`; `if (rows.length < batch) return done()`. The full verifier recomputes only rows it finds, and never compares its final sequence/hash against a separately protected high-water mark. Deleting the latest row(s), or all rows, yields a self-consistent shortened chain reported `ok`; the incremental verifier can catch removal of its checkpoint anchor, but the weekly full check does not use it. **Fix:** verify against an independently protected monotonic checkpoint/head (including on full checks), and alert if the observed tail is behind it; anchor the head outside the mutable database for a privileged-DB-adversary threat model.

4. **Medium — automatic site-outage resolution bypasses the append-only audit trail.** `server/src/services/site-outage.ts:43-55`: `SELECT a.id ... WHERE ... EXISTS (...)`; `UPDATE alerts SET state = 'resolved' ... WHERE state <> 'resolved' AND id IN (...)`; returns `{ raised, resolved }` without `audit(...)`. A restored/stale heartbeat can close multiple major alerts without a corresponding audit entry explaining each transition; the check and update are also separate snapshots, so a cabinet can stop reporting before the UPDATE while the alert still closes. **Fix:** recheck liveness in the UPDATE against current data and append resolution audit entries in the same transaction, at least one per affected alert (or a verifiable batch with IDs).

5. **Medium — security-alert repeat updates change security evidence without an audit entry.** `server/src/services/security.ts:27-37`: `WHEN MATCHED THEN UPDATE SET occurrences = ... detail = s.detail, title = s.title`; `if (r.created) await audit(...)`. Every repeated security signal overwrites its prior detail/title without recording the mutation in `audit_log`; an operator cannot reconstruct the original evidence from that trail. **Fix:** append an audit record for the matched case (or keep immutable per-occurrence evidence and audit its creation), transactionally with the MERGE.

6. **Medium — retention changes/deletes durable records before auditing the run.** `server/src/services/maintenance.ts:149-181`: `DELETE TOP ($1) FROM events ...`, `UPDATE TOP ($1) commands SET result = NULL ...`, then `await transaction(pool, c => audit(... "retention.run" ...))`. Each batch autocommits; a failure or restart before the final append leaves destructive changes without any audit record. `clearOldEventDetail` similarly advances a cursor after clearing (`:125-136`). **Fix:** write an audit entry in each destructive batch's transaction with table/cutoff/count/cursor, or persist a durable run journal before the first batch and record each checkpoint and failure; keep retention configuration bounds enforced independently.

7. **Medium — cabinet detail and site list are unpaginated and scale with site size.** `server/src/services/fleet.ts:65,79-96`: `SELECT ... FROM cabinets ... WHERE k.site_id = $1 ... ORDER BY k.name` and `siblings: siblings.map(cabinetRow)`; `server/src/console-api/fleet-routes.ts:33-48` returns entire objects. A site holding a large share of 8,000 cabinets makes every cabinet view read and serialize all its peers, including per-cabinet correlated open-alert counts (`fleet.ts:26-27`); one repeatedly refreshed page can amplify DB and response load. **Fix:** paginated/keyset site and peer endpoints, bounded peer-summary subset plus total, and aggregate alert counts once for the page.

8. **Medium — fleet-wide reading search repeatedly ranks and counts all stored command results.** `server/src/services/readings.ts:155-167`: `ROW_NUMBER() OVER (PARTITION BY cm.cabinet_id ORDER BY cm.result_at DESC)` over `commands`, JSON predicates on each latest result, then a second `COUNT(DISTINCT cm.cabinet_id)` scan. At 8,000 cabinets with long-lived command history this is expensive even though output is capped; `server/src/console-api/reading-routes.ts:14-17,48-58` limits only one search per user/process for 15 seconds, not aggregate fleet concurrency. **Fix:** maintain/index a per-cabinet/per-operation latest-read projection and precomputed coverage count; impose a fleet-wide concurrency budget and use bounded, server-owned search scope/rate controls.

9. **Medium — on-demand chain verification is a full, synchronous unbounded read.** `server/src/console-api/manage-routes.ts:91-94`: `return verifyChainAndAlert(o.pool, { userId: u.userId });`; `server/src/db/db.ts:384-399` reads the permanent `audit_log` in a loop until exhausted. Repeated Admin requests can run simultaneous whole-chain traversals and SHA-256 computation on an ever-growing log, competing with ingest and the audit append lock. **Fix:** queue/dedupe one verifier globally, return a job ID/status, cap resource consumption, and schedule full checks off-peak while retaining anchored incremental checks.

10. **High (known Phase 2 blocker) — compiled upgrade trust list is empty.** `contracts/trust/upgrade/upgrade-keys.json:2-4`: `"keys": [], "publishers": []`; `server/src/services/releases.ts:72`: `if (this.keys.size === 0) return { ok: false, why: "no release key is configured..." }`. The server rejects every proposed signed release, and an existing agent with this compiled trust bundle cannot install an unsigned or unknown-key release. **Fix:** provision a real offline/KMS signing key's public half and the approved publisher chain, compile them into a separately signed agent release before attempting rollout, and verify the agent's actual compiled trust before publishing. Do not work around by disabling agent signature verification.

11. **Medium (documented architectural boundary, not an existing cross-site bypass) — all support roles have fleet-wide read reach.** `server/src/console-api/fleet-routes.ts:33-43`: `guards.role(request, "tier1")` then `fleet.site(o.pool, id(request))` / `fleet.cabinet(o.pool, cabinetId)`; `server/src/console-api/reading-routes.ts:20-31` likewise accepts any cabinet ID. `docs/spec/09-open-decisions.md:395` explicitly says every signed-in support person sees every client. This is intentional today, but if partner/client accounts or site-restricted operators are introduced, relying on UI filtering or caller-provided `clientId`/`siteId` (`readings.ts:151-159`) leaks cross-site stored reads and command results. **Fix:** add server-owned user-to-client/site grants and enforce them in every detail/list/search/command SQL predicate (not in a separate check before an unscoped query); test unauthorized IDs and concurrent reassignment.

12. **Low (hypothesis: only if the static directory can contain an untrusted symlink) — public static file resolver follows links out of its root.** `server/src/console-api/server.ts:181-190`: `file.startsWith(root + sep) && existsSync(file) && statSync(file).isFile()` then `readFileSync(file)`. The lexical path prefix check does not constrain the real target of a symlink in `console/dist`; an attacker able to place a symlink in that directory can serve an arbitrary readable server file publicly. **Fix:** keep deploy directory non-writable to untrusted principals and resolve/verify real paths or open no-follow with a pinned root; only serve an explicit build manifest.

## Boundaries and negative checks

- Step-up tokens are 32 random bytes, hashed at rest, action+target+user+optional params-hash bound, consumed by a conditional `UPDATE ... used_at IS NULL` in the caller's transaction (`server/src/auth/stepup.ts:12-17,36-45`). TOTP codes are claimed with conditional `totp_last_step` updates (`server/src/console-api/auth-routes.ts:118-125,221-227`). I did not find a source-supported replay/reuse bypass in these paths. Some actions intentionally use click confirmation or optional step-up; do not mistake console hiding for authorization: catalog role and confirmation rules are checked again in `services/console-commands.ts:22-33` and `services/commands.ts:29-36,66-84`.
- Exact Origin is enforced for every non-GET/HEAD console request in `server/src/console-api/server.ts:114-118`; API responses get `Cache-Control: no-store` in `:103-111`, and static HTML gets `no-cache` (`:188-192`). These protections are at the Node app; proxy/CDN overrides are **unverified hypothesis** and need deployment tests. GET `/api/auth/totp/setup` creates or returns an enrolled pending secret (`auth-routes.ts:129-140`) despite GET semantics, but it requires a live session, has `no-store`, and no cross-origin read permission was evident.
- Dynamic SQL examined in server paths uses constants/closed table-name sets and parameterized data; e.g. `services/readings.ts:46-49,150-163`. `db/db.ts:386` interpolates the numeric `batch` into `TOP`; current callers pass constant 10,000 (`maintenance.ts:17`). No demonstrated request-controlled SQL injection was found. A separate `sqlrun` helper was not present in this read scope; do not infer it is safe without reviewing its actual script. Keep identifiers allowlisted/quoted and reject arbitrary user-originated SQL.
- The 18 unexercised live write operations remain a **test/rollout gap**, not evidence of an exploit. No destructive or DB commands were run during this audit.

## Proposed bounded file-version read (design requirements)

There is no existing arbitrary-path read operation to bless. Only a server administrator/deployment owner should set a signed, versioned per-application list of exact paths (or canonical directory roots plus fixed relative filenames); Tier 1/Tier 2 and cabinet agents must not submit paths or mutate the allowlist through a generic command. Prefer retrieving a declared product/file version from trusted metadata; if content is necessary, extract only a defined version field from a specified text format, never return raw content or arbitrary file bytes. Canonicalize and validate a relative path after expansion, reject absolute/traversal/UNC/device/alternate-stream forms as applicable, and ensure the *opened handle* stays inside the approved root. On Windows, reject or safely resolve reparse points/junctions/symlinks and verify the final handle path; on other hosts use no-follow/openat-style descent. Lexical prefix checks alone are insufficient. Require approved file type/ownership/ACL, no network shares, small per-file and aggregate byte caps, bounded file count, timeouts, no directory recursion, and no following changes between check and open. Return only path identifier, normalized version, observed timestamp and bounded status/error; redact secrets, audit each request and per-path outcome, rate-limit and schema-cap the response. Treat cabinet-reported values as untrusted telemetry and associate with the authenticated cabinet ID.

## Data-lite telemetry and peer recommendations (design requirements)

Shrink **payload and frequency**, not the alerting contract: keep authenticated heartbeat/last-seen, cabinet identity and version, command poll/ack/result, critical security events and event cursors, health transitions and incident-triggering event metadata, reboot/crash and disk/availability thresholds. Send bulky raw event detail, full configuration snapshots, software/device inventories, process/service lists and high-frequency load samples only on change, incident or bounded on-demand request; batch/dedupe/compress, enforce age/size limits, and record dropped counts and completeness so a missing sample is not mistaken for healthy state. Preserve offline/site-outage and security alert evaluation; explicitly test both normal and lite modes against the same alert fixtures and long disconnection/reconnect. For peer suggestions, limit candidates server-side to same client/site and compatible role, model, software baseline and data freshness, return bounded ranked summaries with an explanation and confidence, and avoid disclosing another client's raw readings through UI or API. Under today's fleet-wide support model, that is a privacy/product boundary rather than an existing isolation policy.

Scope notes: `docs/spec/10-scale-and-operations.md` was not present at the requested path. The upgrade specification and open-decisions document describe signing and the still-missing key/publisher provisioning; no live release or agent binary was inspected. This audit is source review, not proof of the deployed console's cache/proxy behavior or SQL execution plans.
