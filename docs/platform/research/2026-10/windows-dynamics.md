# Windows platform dynamics — Cabinet diagnostic agent

Scope: engineering decisions for new work, not a redesign of existing `usb.ports`, `devices.list`, `peripheral.status` (including its 24-hour event-410 reconnect count), ScannerWatch, four-target `network.test`, watched-service recovery, firewall snapshots, or the two-minute network/firewall safety net. Repository baseline: `docs/spec/04-agent-spec.md`, `12-milestones-8-to-12.md`, `13-roadmap.md`. The agent is a signed, self-contained .NET 10 two-process service; broker-only privileged operations remain typed and bounded. No arbitrary scripts, shell, free-form network targets, or unrestricted file reads.

## Floors, editions, and device behavior

- **.NET 8, 9, 10:** Microsoft's *currently supported operating systems*, for **all three**, include Windows 10 **1607 LTSC/Enterprise** (OS build **14393**), 1809 (17763), 21H2 (19044), and supported Windows 11 editions; x86/x64/Arm64 are listed. Publishing self-contained bundles the runtime but **does not lower the OS API floor** or bypass OS lifecycle. This makes .NET 10 LTS a supported choice on a supported/serviced 1607 Enterprise/LTSB cabinet, with an architecture-matched build and real-cabinet smoke test. It does **not** prove a binary cannot launch on older unsupported builds, nor make ordinary out-of-support Windows 10 22H2 supported. Microsoft's table does not give a distinct self-contained-only minimum; **14393 is the earliest explicitly supported Windows 10 build, not a demonstrated hard loader minimum**.[1][2][3][4][13]
- LTSC/IoT is a **SKU plus a specific release**, not synonymous with Windows 10 or absence of PnP/WUA. Microsoft's IoT history lists Windows 10 IoT LTSC 2019 **17763**, LTSC 2021 **19044**, Windows 11 IoT LTSC 2024 **26100**. Windows 10 IoT LTSB 2016 is the **14393** generation, but its final monthly update was October 2026: verify actual servicing entitlement before promising continued support. Enterprise LTSC and IoT licensing/servicing differ; do not infer an update offer from a build alone.[5][1]
- Windows `Win32_DeviceChangeEvent` exists for device-change notifications; documented `EventType=2` arrival, `3` removal. These are **generic** changes, not per-port device identities. Prefer `CM_Register_Notification` by device interface/instance, then re-enumerate and join instance ID, hardware ID and stable hub/port location from the existing `usb.ports` inventory; timer starts only after confirmed absence at that location, with a startup/reboot reconciliation. The native notification API is documented for Windows 8+; no Win10/11 gate required. Keep transitions idempotent and key by location+expected identity, so duplicate/log-replay events cannot inflate an N-in-Y reconnect count.[6][7][32]
- Kernel-PnP **410** ('Device started') is the existing scanner reconnect **proxy**, not authoritative proof of a physical unplug/replug; configuration-channel IDs **400** ('configured') and **411** ('had a problem starting') and **420** (removal-like records) must not be treated as a universal, authoritative arrival/removal taxonomy. I could not confirm a Microsoft-published cross-build event-ID contract for these IDs: correlate the exact channel/provider/instance ID and `Get-WinEvent` XML against real 14393/17763/19044/22621/26100 fixtures before assigning semantics. Use native PnP current state for alert truth, event records only as supporting history.[6][7]
- USB selective suspend can suspend **one hub port** independently; it is **enabled by default** and Microsoft strongly discourages blanket disabling. A sleeping port is not automatically a missing device: distinguish a present devnode with a power transition from a truly absent one. USB 3.x has `Usbxhci.sys` and `Usbhub3.sys` xHCI/root-hub topology. Windows 11 USB4 adds OS-managed USB4 **routers** (`Usb4HostRouter.sys`, `Usb4DeviceRouter.sys`) that need not map one-to-one to the USB3 `Port_#...Hub_#...` convention; probe actual connection topology rather than equating routers to USB3 hub ports. Microsoft says OS-provided USB4 connection manager is required starting Windows 11; no precise earliest Windows 11 sub-build for every USB4 topology API was confirmed.[8][9][10]
- Service re-attachment on device arrival: map expected device identity/location to a **server-approved service or executable identity**, not an arbitrary path; after PnP stabilizes query SCM status/start type, dependencies and service process, then invoke only existing broker service-watch/start logic within its refusal list, backoff and limits. A process-only dependency needs a separate signed-package/allowlisted `app.restart` operation, not `Start-Process` from server data. `QUERY_SERVICE_CONFIG` exposes dependencies; a service can be absent, disabled or protected. Protected anti-malware services cannot be stopped by a normal admin process, so even LocalSystem is not blanket authority; report `unsupported/protected/access_denied` instead of trying to force them.[36][19]

## Windows Update: capability, policy, and reboot contracts

- Windows Update Agent (WUA) COM supplies search, download, install and per-update results (`IUpdateSearcher`, `IUpdateDownloader`, `IUpdateInstaller`); search criteria include installed state and type. Keep the existing `updates.status`; new check/install/schedule/defer actions are broker-scoped, explicit about source (Windows Update versus managed WSUS), update classification, acceptance, progress, timeout and reboot. Never assume `updates.install` plus `NoAutoReboot` suppresses a **separate OS-managed policy deadline**. Search results and policies depend on update source, service availability, eligibility and servicing state; unavailable is not 'fully updated'.[11][12][15][35]
- **Registry is not a single portable policy API.** For Group Policy, Microsoft documents `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate` and values `DeferFeatureUpdates` + `DeferFeatureUpdatesPeriodInDays` (0–365), `DeferQualityUpdates` + `DeferQualityUpdatesPeriodInDays` (0–35 in the older GPO table), and `ExcludeWUDriversInQualityUpdate`. The Policy CSP uses `./Device/Vendor/MSFT/Policy/Config/Update/...`, with different policy storage under `PolicyManager`; setting a similarly named registry value does not emulate MDM enrollment. Inventory **both** effective GPO/MDM ownership and WUA scan source before attempting a change; Group Policy refresh or MDM can overwrite local writes. Microsoft's current CSP page specifies the quality deferral range **0–30**, while the older GPO summary says **0–35**: do not hardcode 35 as a universal modern limit; prefer managed policy interface and actual supported range.[14][13][35]
- **Windows 10 vs 11 and patch floors:** CSP `DeferFeatureUpdatesPeriodInDays`, `DeferQualityUpdatesPeriodInDays` and `ActiveHoursStart` apply from Windows 10 **1607/14393** onward; `ActiveHoursMaxRange` from **1703/15063**. **Do not use** legacy `BranchReadinessLevel` as a Windows 11 feature-update channel gate: Microsoft calls it inapplicable to 11. 1607 pause keys (`PauseFeatureUpdates`, `PauseQualityUpdates`) differ from 1703+ `PauseFeatureUpdatesStartTime`/`PauseQualityUpdatesStartTime`; newer-version keys take precedence over legacy keys. Feature/quality pause is temporary (35 days), not an indefinite fleet hold.[13][14][31]
- **Target-release pin:** `TargetReleaseVersion` policy became available on 1803 at **17134.1488**, 1809 at **17763.1217**, 1903 at **18362.836**, and generally from 2004/19041; its matching `ProductVersion` floor is **19041.1202** (2004 + KB5005101) or **22000** (Windows 11 21H2). The CSP requires ProductVersion alongside TargetReleaseVersion. For GP, inventory `TargetReleaseVersion` (enable DWORD), `TargetReleaseVersionInfo` (version string) and `ProductVersion` (Windows 10/11 product string); Microsoft's CSP docs establish GP path but **do not unambiguously specify these three raw GP value encodings on every legacy ADMX**, so verify on a target machine using installed ADMX/`gpresult` before directly writing. On 14393 there is **no documented target-release policy support**; use an external management/approval path, not a pretend registry pin.[13]
- **Active hours and deadlines:** documented GPO registry values are `SetActiveHours`, `ActiveHoursStart`, `ActiveHoursEnd` under the WindowsUpdate path. 1607's maximum active-hours span is **12 hours**; later versions allow **18**. `ConfigureDeadlineForQualityUpdates` CSP begins at **1903/18362**; the Windows 10 22H2 compliance-deadline family differs from Windows 11 **22H2/22621+**, which offers separate `ConfigureDeadlineNoAutoRebootForQualityUpdates` and `...ForFeatureUpdates`. At a deadline Windows may restart even during active hours. `NoAutoRebootWithLoggedOnUsers` is legacy and not a reliable universal guarantee; it can prevent quality-update restarts indefinitely. Surface pending restart and deadline in the UI, maintain independent agent-scheduled restart state, and require a human-approved maintenance window. Do not claim Windows Update reboot scheduling is equivalent to the agent's `system.restart` schedule.[16][15][13][31]
- **Self-reverting policy application:** prefer centrally owned GPO/MDM change rather than local registry writes. If authorized local policy is allowed, snapshot *value existence, type and data* (including conflicting AU/WSUS keys), record owner, set expiration in broker-persisted state **before** change, apply one typed allowlisted policy, read back the effective setting and WUA behavior, and restore exactly the original absence/type/value at expiry or loss-of-contact. Recheck after Group Policy refresh/reboot and mark `superseded` rather than fighting enterprise management. A process timer alone or a registry readback alone is not a verified revert; recover missed expiries at service boot. This extends, rather than silently replaces, the existing two-minute network/firewall safety net.[14][15][35]

## Deployment scripting: PowerShell 5.1 Desktop vs 7.x Core

- Launch the intended engine by **full path** (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe` for in-box 5.1, explicit installed `pwsh.exe` for 7); test `$PSVersionTable.PSEdition`, `.PSVersion`, `[Environment]::Is64BitProcess`, `$ExecutionContext.SessionState.LanguageMode` and `Get-Command`/`Get-Module -ListAvailable`. PowerShell 7 is side-by-side, not a replacement; don't rely on PATH/`powershell` to select it. Use PS5.1 parse-compatible syntax across both: avoid `??`, `??=`, `?.`, ternary `? :`, `&&`/`||`, parallel `ForEach-Object`, and PS7-only cmdlet parameters in shared files; branch only **after** a PS5.1 parser can parse the file.[20]
- `Get-CimInstance` (CimCmdlets) is available in 5.1 and 7; deprecated `Get-WmiObject` exists only in Windows PowerShell 5.1, **not** 7+. Prefer CIM with capability probe for WMI inventory; do not assume a CIM class or provider's device attributes are populated on all OEM SKUs. `Test-Connection` differs: 5.1 documents `-ComputerName`, `-AsJob`, `-Count`, `-Delay`, `-Quiet`; 7 documents `-TargetName`, `-TcpPort`, `-TimeoutSeconds` and different output types. Use common `-Count/-Quiet` only after probe; for bounded RTT/loss/jitter use .NET `Ping.SendPingAsync` with cancellation/timeout and explicit N, not parsing `ping.exe` or assuming `-TcpPort` in 5.1. `Test-NetConnection -Port` belongs to Windows `NetTCPIP`, **not** a PS7 cross-platform built-in: `Get-Command Test-NetConnection`; otherwise bounded `TcpClient.ConnectAsync`, using only existing four targets and approved ports.[21][22][23][24][34]
- Windows PowerShell 5.1 runs on .NET Framework; 7 runs on modern .NET. Older Framework installations can choose legacy TLS defaults: inspect `[Net.ServicePointManager]::SecurityProtocol`, OS Schannel and Framework `SchUseStrongCrypto`/`SystemDefaultTlsVersions`; on PS5.1 where needed explicitly select TLS 1.2 for that process, but never lower server TLS. Microsoft's best practice is OS-default TLS on suitably configured recent Framework, rather than a permanent `Tls12` pin. Windows 10 normally ships Windows PowerShell 5.1; do not install WMF 5.1 as a default Windows 10 step. For older/downlevel hosts needing WMF, check Microsoft's WMF installer prerequisites including .NET Framework (and reboot); the downloadable WMF is not a prerequisite for a self-contained .NET 10 agent.[26][27][1]
- 32-bit scripts on x64 see WOW64 filesystem redirection: `System32` can map to `SysWOW64`; `Sysnative` is a 32-bit alias for real 64-bit `System32`. Deploy x64 broker/agent on x64 cabinets, validate architecture and use absolute tool paths; don't infer actual OS architecture from process bitness. Win10 **1607+** long-path Win32 support requires both `LongPathsEnabled` policy and executable `longPathAware` manifest and does not automatically fix legacy shell/cmdlets; validate/limit server-provided file paths, canonicalize, deny reparse/UNC/out-of-root traversal, and treat inaccessible paths as `could_not_check`.[28][29]
- Execution policy is not an access-control boundary; WDAC/App Control can force disallowed scripts into **ConstrainedLanguage** even when execution policy permits, and audit-mode UMCI can constrain interactive PowerShell. Signing an agent executable does not grant every script FullLanguage: separately allow `.ps1`, `.psm1`, `.psd1` or avoid scripts by implementing native typed operations. Especially on Windows 10 **1607 LTSB**, App Control's `Disabled:Script Enforcement` option is unsupported. Defender ASR blocks obfuscated scripts from Win10 **1709** and PSExec/WMI-origin child processes from Win10 **1803** in supported deployments; audit/block state and protection events before package deployment, never advise disabling Defender globally.[18][17]
- `icacls` is a native executable with `/grant:r`, inheritance, SID syntax, `/verify`; ACL evaluation isn't a PowerShell-edition feature. Use well-known SIDs rather than localized account names, set owner/inheritance deliberately, read back effective ACL and reject unintended Users write; don't confuse a successful `icacls` exit with service-account access. ScheduledTasks and NetTCPIP are Windows modules, not guaranteed PS7-native: probe `Get-Module -ListAvailable`, try native import, and when required `Import-Module ScheduledTasks -UseWindowsPowerShell` on PS7, understanding that implicit-remoting outputs are **deserialized**, not live CIM objects. Prefer Task Scheduler COM/SCM APIs for the .NET broker; scripts use `Get-Service`/`Start-Service` only for allowed names, and `sc.exe` by full path where start-type/recovery semantics need it. Never rely on platform-dependent output objects or `Set-Service` supporting the same parameters everywhere.[30][25][24][19]

## Dynamic detection and acceptance gates

1. At enrollment capture OS build+UBR+edition+architecture, servicing/ESU entitlement, app-control/ASR mode, PS engine/module inventory (diagnostics only), WUA managed source and effective update policy/owner. **Build gates only where Microsoft documents floors**: 14393 baseline CIM/WUA/active-hours, 15063 maximum active-hours-range, 17134.1488/17763.1217/18362.836 release target, 19041.1202/22000 ProductVersion, 18362 quality deadline, 22621 separate no-auto-reboot deadlines. Prefer exact installed KB/UBR over marketing 'Windows 10/11'.[13][15][17][18]
2. Probe at execution: enumerated expected port and devnode presence; native PnP subscription and re-enumeration; WMI/CIM class availability; USB topology/capability; SCM access and service dependencies/protection; WUA scan result/classification/source and pending reboot; policy owner/effective value; script engine commands/parameters and language mode. Disabled channel/provider or missing hardware = `unsupported`/`could_not_check`, not zero reconnects or green health.[6][7][10][11][19][20]
3. Server feature flags describe **authorized intent**, never fake capability: allowed per-location identities, absent-X and N-in-Y bounded thresholds, approved service/app mapping, four bounded packet-loss destinations/probe count and rate, approved absolute application-version paths, allowed update classes/windows, policy value allowlist and expiry. Enforce limits locally; use monotonic elapsed-time plus persisted wall timestamps across reboot, state-change deduplication, and post-write verification/restore. `FileVersionInfo.GetVersionInfo` reads version resources of allowlisted files; it is metadata, not proof that an application is installed/healthy. For packet loss report sent/received, latency distribution and sample jitter only for successful probes; with no replies jitter/RTT is **null**, not zero.[33][34]

## Explicit uncertainties requiring test fixtures

- No authoritative source found establishing a **hard executable/load minimum** for a .NET 8/9/10 *self-contained* binary distinct from Microsoft's supported-OS table; treat Windows 10 **14393** as earliest documented **support** floor, not a proven loader threshold.[1][2][3][4]
- No Microsoft cross-build mapping found that makes Kernel-PnP **410/420** an authoritative physical reconnect/remove pair; event 410 remains an existing scanner heuristic, not a general per-port counter. Capture provider, channel and XML on actual cabinets.[6][7]
- No authoritative guarantee that an arbitrary old LTSC USB hub, CIM provider, USB4 router or third-party service presents a stable `Port_#...Hub_#...` mapping after topology changes; bind to expected hardware ID plus observed location and mark ambiguity, never silently remap.[9][10]
- No authoritative, version-independent raw-registry write contract confirmed for all `TargetReleaseVersion`/`TargetReleaseVersionInfo`/`ProductVersion` **GPO** combinations on legacy ADMX. Use CSP/GPO tooling and verify on each supported build rather than promising registry-only deferral/pinning.[13][14]
