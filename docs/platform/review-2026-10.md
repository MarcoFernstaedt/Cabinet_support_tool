# Repository review, October 2026

A full pass over the repository once all seven milestones, per-client device settings and the 8,000-agent load test were done. Separate reviewers covered the agent, the server, the console with the contracts, and repository hygiene. Each finding was checked against the code before it was fixed. This page records what was fixed, what was left and why, and what is recommended next.

Measured performance (the command round trip, heartbeats, events, and the load test) is in [performance.md](performance.md).

## Fixed

### Agent

| Finding | Severity | Fix |
|---|---|---|
| The SYSTEM broker and updater worked through folders the network service can write (`downloads`, `logs`). By turning one into a junction, a compromised network service could make SYSTEM set an access list, delete, move or overwrite files anywhere. That is a route to SYSTEM. | Critical | The broker and updater now log to `broker\logs`, which only SYSTEM and administrators can write. The broker only *reads* downloads; the network service deletes its own package and release downloads, and sweeps leftovers when it starts. At each start the broker re-creates `downloads` with its access list set at creation, removes a junction planted in its place, and refuses to start if a broker folder is a link. |
| Before installation, any user could create `C:\ProgramData\Mashura` and own it. | Medium | The installer refuses a Mashura folder that is a link or not owned by SYSTEM or Administrators, then locks it down. |
| A package install was cut off at 90 s on the network side and 2 min on the pipe. A long MSI was reported as `timeout` while it carried on installing. | Medium | Time limits are now set per operation kind (install 20 min in the broker, 29 min overall; other writes 5 min). The pipe limits only reading and writing a message. A test checks that the network side always outlasts the broker. |
| A network or firewall change that failed half way (address set, then the gateway refused) threw before the safety net was armed, which could strand the cabinet. | Medium | The safety net is armed with the state from before the change. A failed command is never confirmed, so the cabinet goes back to that state at the deadline. |
| The updater counted a check-in that an old network service could write in advance, with a future time. | Low–Medium | A check-in counts only if it is dated after the new version started and not in the future. |
| An upgrade offer that arrived while the agent was busy was lost until the next restart. | Low | It is not marked as tried until it is actually tried. A broker that is busy or unreachable leaves it to be tried again. |
| The install token was passed on the command line, where process auditing can record it. | Low | A new `-BootstrapTokenFile` option; the console's install steps use it. |
| The development release-key path was checked differently from how it was written, so a relative path could land inside the repository. | Low | The check and the write now resolve the path the same way, and the key file is readable only by its creator. |
| Exception text appeared in updater logs. Service names were written out in two places. | Low | Fixed. |
| An update could rename a firewall rule, giving a Windows rule the platform's prefix or taking it away from a platform rule. | Medium | The agent and the server both refuse a rename. |

### Server

| Finding | Severity | Fix |
|---|---|---|
| A correct password reset the failure count, so someone holding a password could guess authenticator codes without ever locking the account. | High | The count is cleared only by a correct code, or by a sign-in that needs no code. Wrong codes also count against the address limit. |
| After a lock ran out, the next single mistake re-locked the account silently. | Low | The count starts again once a lock ends, so a new run of failures locks again and raises a new alert. |
| Successful step-ups were not audited (spec control 12). | Medium | Each granted step-up is audited with its action and target. |
| A renewed certificate left the old one valid, and renewal could be repeated. | Medium | The new certificate's first use revokes the old one. A certificate whose successor has been used cannot renew. A successor that was never used (the answer was lost) is withdrawn and replaced, so the agent can simply ask again. |
| Delivered commands never expired, so the console could show them as running forever. | Medium | They expire 35 minutes after delivery (longer than any agent limit). A result that arrives later is still stored. |
| The live stream stopped reconnecting after one failed attempt. | Medium | It retries with a growing pause (1 s up to 30 s). Both listeners close the failed connection. |
| `CONSOLE_TRUST_PROXY=1` trusted the client-written left end of `X-Forwarded-For`. | Medium | The setting is now a hop count, or the proxies' own addresses. Only the address the nearest trusted proxy saw is used. |
| Rollouts targeted cabinets below the release's minimum version. Their refusals paused the rollout for nothing. | Medium | Those cabinets are left out, and the count is recorded in the audit entry. Targets are written in one statement without locking every cabinet row, so heartbeats are not held up. |
| Opening a stored event was not audited (spec 05). | Medium | It is now audited as `event.open`, with the cabinet as the target. |
| Slow paths: an unbounded, unindexed sort on each event detail; a cabinet's event list took 101 queries; a full scan of the commands table for history and package downloads; the live stream loaded every alert even with nobody connected. | Medium | Migration `0009` adds indexes (`events.received_at`, `commands(cabinet_id, issued_at)`, and delivered commands). Event lookups are bounded to 30 days, the event list is one query, and the stream skips the work when nobody is listening. |
| The CLI skipped the console's role, Admin-only and approved-package rules. | Low | Both paths use one function. `09-open-decisions.md` is updated. |
| Authenticator setup created a new secret on a GET. | Low | The pending secret is created once and shown again until setup completes. |
| The fleet search query was checked by hand, not against a schema. | Low | It is now checked against the new `console/fleet-search` schema, with hostile examples. |
| The per-address failure map could grow without limit. | Low | It is pruned. |

### Console and contracts

| Finding | Severity | Fix |
|---|---|---|
| A Tier 2 user could create an inbound "allow everything" rule, which has the same effect as turning the firewall off with no time limit. That is Admin only. | Medium-High | The server refuses an inbound allow rule from a non-Admin unless it names a port, a remote address or a program. |
| Moving from site A to site B kept A's values in the editors, so Save wrote A's settings onto B. | Medium | Loaded data belongs to its path and is dropped when the path changes. The editors are keyed by the site's or client's id. |
| `/cabinets/%E0` crashed the whole console, and encoded `../` in an id could redirect the API call a page built from it. | Medium | Route parameters must be UUIDs (or plain words), and decoding is guarded. A per-page error boundary keeps one page's failure from blanking the console. |
| The audit page showed a cabinet name taken from the link, so the label could be spoofed. | Medium | The name comes only from the server's audit entries. |
| A typo when approving a cabinet silently created a new client or site. | Medium | Existing clients and sites are offered. A name that differs from an existing one only in capitals is refused. The confirmation says when a new client or site will be created. |
| Waiting for a result depended on the browser's clock. | Low-Medium | The wait is measured on the browser's own clock from the server's issue and expiry times, and the result is always checked at least once. |
| Smaller issues: notes length (500 in the console vs 256 in the schema); names lost when a confirmation was cancelled; duplicate ports allowed; object URLs never released; no upper bound on the write limit; Edit DNS not disabled during a write; free-text suppression log. | Low | Fixed. Suppression logs are offered from a list. |
| The Alerts page had no client or site filter (spec 06). | Spec gap | Added. |

## Left as they are, with the reason

- **Map to issue does not pre-fill a device hardware ID from an event log entry.** Live event log entries carry no device. Monitor events that do carry one are mapped from their alert, which does include it.
- **Step-up tokens are bound to user, action and target, not to the exact parameters.** A token is single use and lasts 2 minutes. Binding the parameters would mean hashing them on both sides and changing the step-up contract, so it is recorded as a recommendation below.
- **Package checks hold a driver zip in memory (up to 2 GB inflated).** Only an Admin can upload, and uploads are rare. The recommended fix (run the check in a worker thread, streaming each entry) is below.
- **The rollout re-counts its batch on every report.** This is a few milliseconds with the index. Counters are recommended only if rollouts of more than 8,000 cabinets are planned.
- **The network service can create the updater's mutex name first, which blocks upgrades.** This is low impact: an attacker who already runs code as the network service gains only a denial of upgrades, which shows as failed rollout targets. The fix is a private object namespace or a mutex with a SYSTEM-only access list.
- **Maintainability splits** (the agent's `AgentConnection.cs`, the console's `Writes.tsx`, shared helpers that still live in files named for something else). These are refactors with no behaviour change; they are scheduled with the console unit tests below.

## Recommendations

### Remove

1. **The earlier C# demo:** `src/`, `tests/`, `tools/`, `CabinetPlatform.sln`, the root `Directory.Build.props`, `demo-correction-checks.yml`, and the demo documents directly under `docs/`. The platform replaces all of it, git history keeps it, and the agent no longer depends on the root props file. Removing it halves what a new developer has to read and removes a second, weaker security model from the repository. *Done (approved): removed in October 2026.*

### Improve

2. **Done: moved to .NET 10.** (Was: move to .NET 10 before 10 November 2026), when support for .NET 8 ends. The agent is self-contained, so cabinets need nothing installed. This is a target-framework change, then a signed upgrade through the M7 channel.
3. **Commit NuGet lock files** (`RestorePackagesWithLockFile`) so agent builds are reproducible, as npm builds already are.
4. **Add console unit tests** (Vitest is the likely choice; it would be a new dev dependency) for the parsing and form logic: ports, firewall rule forms, addresses, route matching. Include hostile input. Everything else in the console is covered by the browser end-to-end tests.
5. **Run package and release checks in a worker thread**, streaming zip entries instead of inflating them all at once.
6. **Bind step-up tokens to a hash of the exact parameters** for writes.
7. **Restore GitHub Actions minutes.** The last runs did not start, so CI has not yet confirmed these changes on the Windows runner.

### Add, for the two goals (diagnose without searching; be proactive)

8. **A "diagnose this cabinet" bundle.** One button runs the common reads (system info, scanner checklist, drives, recent errors, network tests to the server and the sync cabinet, firewall state) and shows one summary of what is wrong, with the matching issue types. Today a support person runs them one by one. This uses only operations already in the catalog.
9. **Daily error trends.** For each issue type and each unrecognized error: how many cabinets, rising or falling over 7 and 30 days, and new ones since yesterday. Most of this is a query over `events`. It turns the collected errors into something the team can monitor rather than just open.
10. **Unrecognized-error triage queue.** Group unrecognized errors by log, source and event ID across the fleet, sorted by how many cabinets reported them. Mapping one group then classifies every cabinet at once. Map to issue already does the mapping; the grouping and ordering is the missing part.
11. **Fleet health checks on a schedule.** A nightly read on every online cabinet (drive health, scanner status, Windows Update age, free disk) stored as a trend. This finds failing drives and stale updates before staff call in. It would run within the existing rate limits, spread across the night.
12. **Notifications outside the console.** Send new major alerts to email or Teams, with a link to the alert. Only the alert title and a link should leave the platform, never event text.
13. **Runbooks on issue types.** A short "what to do" text and links on each issue type, shown on every alert of that type, so the fix travels with the diagnosis.
14. **Resolution notes that feed back.** When an alert is resolved, the chosen cause and fix become statistics on its issue type ("usually fixed by reinstalling the scanner driver"), so the most likely fix is suggested first next time.

Items 8 to 14 stay within the security model. None needs a new kind of agent operation except possibly item 11's schedule, which is server-side. Each would be its own milestone, specified first in `docs/spec`.
