# Password demo BFF — source-only boundary

`CabinetPlatform.DemoBff` is a **separate demo-only** ASP.NET Core process. It does not modify the fail-closed Entra `CabinetPlatform.WebHost` and is **not** staff sign-in or product acceptance. Its only routes are `GET /`, `POST /login`, and `POST /logout`. It does not serve sample cabinet data, proxy arbitrary API paths, or provide cabinet access. The Node synthetic preview is separate and is not a fallback on failed Server login.

The BFF sends the submitted password over HTTPS to the existing Server `POST /api/auth/login`, whose account verification, lockout and IP limiting remain authoritative. It retains only the short-lived access JWT in an in-process, bounded session dictionary; it discards the upstream refresh token. The browser receives a random opaque `__Host-DemoSession` cookie (Secure, HttpOnly, SameSite=Strict, Path=/), never an API bearer. The server stores a digest of the cookie key. Sessions have an absolute expiry capped at the upstream access-token expiry and 15 minutes, plus a 10-minute idle cap; logout removes the server entry. Restart destroys all sessions. A session has **no cabinet authorization** and must not be used as authorization for new routes.

The host fails startup unless `DemoBff__PublicOrigin` and `DemoBff__ServerBaseUrl` are exact HTTPS origins (e.g. `https://demo.example` and `https://server.example`). The incoming HTTPS scheme and exact Host must match the public origin. Bind this process only to an operator-controlled HTTPS ingress, or configure trusted proxy forwarding in a separately reviewed change; do not trust arbitrary forwarded headers. The Server must be accessible only through trusted network policy and certificate validation; do not expose its password API to an untrusted network. No development HTTP bypass, credential defaults, sample fallback, or embedded secret is provided. Form POSTs require both exact Origin and ASP.NET antiforgery validation; ingress POSTs are rate-limited per observed remote IP, with no trust in `X-Forwarded-For`. Browser-visible denials do not contain account status, passwords or Server error bodies.

This does **not** implement MFA, Conditional Access, staff-to-site/cabinet grants, password-change UX, Server deactivation/revocation propagation into the in-memory session, distributed session storage, or real-data projections. Before any real cabinet data, separately design narrow typed BFF routes enforcing Server-side scoped authorization on every request, account revocation, privacy/retention and audit, TLS ingress, credential-rate-limit partitioning behind an approved proxy, independent security review, browser accessibility and native Windows/HP acceptance. No live Server/HP credentials or deployments are used in its tests.
