# Office lab device credential renewal

This manual operation renews one already enrolled, approved, active device with its original protected Agent key. It is not fleet renewal or key recovery. No live deployment or device check was performed here.

## Package and prerequisites

Include `tools/office_renewal_operator.py` with the server and operator kit as a separate named file. It requires Python 3.10 or later, a trusted TLS certificate for the exact server hostname, and a local private directory for the decision file. It uses only the Python standard library. Do not put a password, access token, refresh token or device key in the command line, environment, chat or file. Run on the service owner workstation or VPS with authorized access, not on the cabinet. The client prompts with masked `getpass`; the Bearer token and password are never deliberately persisted. The Python process and host still need normal operator protection. Do not enable HTTP wire tracing or proxy credential capture. The server logs and TLS termination are separate acceptance gates.

Confirm the matching server revision, OfficeEnrollment enabled, the original private consumed token journal and matching configured token hashes, trusted server time, protected Agent `.device` journal on the SAME physical device, and an approved active cabinet with nonempty historical heartbeat data. The helper reads the cabinet detail and heartbeat history but approval and local key presence require operator confirmation through the approved cabinet view and the device's protected installation. Never copy or print the key. If missing, stop. Suspected key theft or compromise is not a renewal case: refuse renewal and follow the observed revocation and retirement procedure. A stolen key with the same machine ID works during any valid window.

Create an operator owned private directory: `mkdir -m 700 /path/to/private-renewal`. Use a unique decision file per intended cabinet decision. For a new decision:

`python3 tools/office_renewal_operator.py --origin https://server.example --username SUPERVISOR --cabinet-id CABINET_UUID --machine-id EXACT_MACHINE_ID --state /path/to/private-renewal/decision.json --reason 'specific lab session reason'`

The arguments are nonsecret; the password is entered privately. Check the displayed cabinet UUID, machine ID, actor ID, prior contact and history, then type the exact machine ID and `YES` only after checking approval, the original device journal and absence of suspected compromise. The helper writes the request UUID, normalized reason, actor ID, origin, cabinet and machine identity, prior contact and history metadata in a 0600 file and syncs it BEFORE posting. It refuses an existing file when `--reason` is supplied. Protect and retain this nonsecret attribution file. It is not a substitute for the server journal. A server response alone does not prove contact.

If the response is lost, a 500 occurs or contact is not yet visible, reuse the SAME file and SAME Supervisor account in a fresh process and omit `--reason`:

`python3 tools/office_renewal_operator.py --origin https://server.example --username SUPERVISOR --cabinet-id CABINET_UUID --machine-id EXACT_MACHINE_ID --state /path/to/private-renewal/decision.json`

The helper rejects redirects and non HTTPS origins, checks current user and role, target activity, identity, history, response UUID and UTC expiry, and looks for a newer check in plus the previous heartbeat ID under the same cabinet. If a new contact has not yet been recorded, leave the file intact, allow the Agent its normal retry, and run the same command later. Concurrent retention or equal timestamp heartbeats can prevent automatic history verification; inspect the protected server history manually, not a new grant. The response of an exact retry is the ORIGINAL expiry. The server binds retries to the Supervisor user ID, not the login session. If that user loses authority, stop and reconcile through authorized review rather than substituting another user or UUID.

A mustChangePassword response blocks renewal until the supported password change workflow completes. HTTP 401 requires sign in again as the same user; 403 means authority denied; 409 can mean a missing or retired cabinet, revoked or missing grant, UUID collision or the 30 decision cap. Do not bypass 409 by clearing a journal, restoring an older snapshot, generating a new request ID for an uncertain outcome, or reenrolling an existing identity. An intentional new day requires a NEW file and UUID only after the previous decision and contact are resolved. No indefinite extension is supported.

## Persistence and rollback

Each decision expires 24 hours after the server records it. The original token permits initial enrollment only for its short configured window, and original device authorization expires at its configured time. At most 30 decisions exist per device. Journal replacement is flushed and exclusive, but file and SQL audit are not one atomic transaction: an HTTP 500 can have recorded an active grant while the SQL success audit is absent. An exact retry can fill in the audit if the cabinet and actor remain eligible. The journal remains authoritative for expiry and attribution. Preserve all journal and database history; never initialize an empty journal to fix startup refusal.

Revocation requires removing the matching token from protected server configuration, stopping and restarting the current server to observe that absence, and verifying the durable tombstone BEFORE considering rollback. The current reader replaces the revoked key hash with a random unreachable hash while retaining the token hash, machine identity and renewal history. This also makes the original key unusable to the baseline ce7f349 parent reader that ignores Revoked, even if an old token configuration is accidentally reintroduced. An already tombstoned journal from the earlier renewal revision must be opened by this corrected reader once to shred its stored key hash before any downgrade. Do not put a baseline reader online beforehand. Keep the exact protected journal and token configuration; do not restore a pre revocation snapshot. Backup rollback can undo the tombstone and is outside this guarantee. The older reader's 128 KiB journal ceiling can also refuse a large renewed journal; that refusal is safe and must not be worked around by resetting history.

For an authorized lab rollback, stop the server; make a consistent protected backup of database, journal, token manifest and config with secrets confined to the approved location. First start this corrected reader with the intended token removals so it durably marks and shreds every removed or previously tombstoned grant. Stop it, preserve the newly written journal unchanged, then start the baseline binary only if the journal is within its limit and all unchanged token configuration paths have been verified. Test an old key and machine pair through the actual baseline reader before exposing Agent routes; it must be refused. Keep Office mode enabled so shared secret fallback cannot revive access. If the reader cannot start or the old key authenticates, stop and restore the compatible corrected reader without resetting grants. Downgrading loses renewed expiry interpretation; stop relying on renewal until this revision is restored. No deployed rollback was performed here.

Authentication rejects times before the latest renewal issue timestamp and at or after its expiry. The server still relies on a trustworthy clock: rollback into an earlier valid window can make a formerly expired grant valid again; tests do not prove monotonic time, crash durability or resistance to restored backup snapshots. Native Windows, TLS at a real server, actual same device contact and deployed history readback remain blocked pending authorized acceptance.
