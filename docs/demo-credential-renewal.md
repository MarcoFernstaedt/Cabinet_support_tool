# Office lab device credential renewal

This is a manual repeat-session operation for one already enrolled, approved and active device. It is not automatic fleet renewal or a production PKI design. Deploy only after independent security review and authorized Windows/server acceptance. The server must be running this revision, OfficeEnrollment must be enabled, and the original consumed-token journal and matching token configuration must still exist. Do not recreate the journal or issue a second enrollment token for the same machine.

## Contract

A signed-in Supervisor selects the existing cabinet UUID from the cabinet detail view and confirms its machine identity. The endpoint is `POST /api/office/enroll/renew/{cabinetId}` with JSON `{"requestId":"<new UUID>","reason":"<specific lab session reason>"}` and a Bearer access token from the existing support login. Use the same UUID, same reason and same Supervisor session for an uncertain response. An exact retry returns the original expiry, not another day. A different request ID is a new explicit operation. The server returns the cabinet UUID, bound machine ID, request ID and UTC expiry. It never returns or accepts a device key. A key already stored in the Agent's protected `.device` journal becomes valid again without reinstalling, changing the machine ID, approval, cabinet ID or history.

Each new decision expires 24 hours after the server receives it. At most 30 renewals are recorded per device; no automatic renewal or unbounded grant. The original enrollment token expires after 20 minutes for first use; the original device grant expires after 24 hours from issuance. Recovery is permitted after that expiry only if the existing grant, its matching configured token hash, the protected server journal, and the approved active cabinet row remain. Removing the token from server configuration and restarting permanently tombstones its bound grant. Readding the same token afterward does not undo that revocation. Retirement's database row lock serializes with renewal; a retired or deleted cabinet is refused, including retries. An operator cannot use a new token to bind the existing identity.

The server journal stores only key/token hashes and renewal metadata: request UUID, Supervisor ID, reason, issue time and expiry. It is atomically replaced under the server's exclusive process lock before a successful response. The regular audit table records authorized successful requests with cabinet ID, actor and request UUID; repeat requests can create additional audit rows but not grants. The journal is the authoritative success and retry record if the response or subsequent SQL audit commit is lost. Do not manually edit it. Missing/corrupt journals prevent startup, and a missing journal during renewal prevents the write. This uses file replacement and flush; filesystem power-loss and backup/snapshot rollback guarantees have not been established. Keep the existing private file and backup policy.

## Operator procedure after review

1. Confirm this exact server revision and its OfficeEnrollment configuration through the authorized deployment channel. Sign in as a Supervisor through the existing support authentication workflow, not with the Agent key. Obtain the Bearer access token through an approved local operator client; do not paste it into chat, logs, shell history or the request body.
2. Open the existing cabinet detail and record its UUID and machine ID. Confirm it is active and that its approval and historical data are the intended device. Confirm the same Windows device still has its original administrator-protected Agent credential journal. Do not copy the key to another device or replace that journal. If it is missing, stop; this operation cannot recover an erased private key.
3. Generate a fresh random UUID in the operator client, write a specific reason, then send the single JSON POST above over the server's validated HTTPS origin with `Authorization: Bearer <access token>`. Never use redirects or an unverified endpoint. Keep the request UUID and exact reason locally until the response is settled.
4. Confirm HTTP 200 and read back the returned cabinet ID, machine ID, request ID and UTC expiry. If the response is lost, retry the identical request with the same authenticated Supervisor. HTTP 401 requires sign-in; 403 means insufficient role; 409 means retired/missing identity, revoked/missing grant, or request UUID collision. Do not work around 409 by reinstalling or recreating the journal.
5. After the Agent's normal retry, confirm an authenticated check-in under the same cabinet and historical detail via authorized APIs. The response alone is not proof of Agent contact. For this worktree, no live server, HP, or Windows check was performed.

Threat boundary: the Supervisor's authenticated account authorizes a bounded grant, while the existing per-device key proves Agent possession. This is not hardware-bound identity: theft of that protected key and machine ID permits impersonation during a valid window. TLS, local file access controls, protected server journal/configuration, trustworthy server clock and authorized operators are required. A compromised Supervisor can manually grant up to the cap; a compromised server or filesystem can replace the journal. Removal of a token that is never observed by a running/restarted server before being readded is not a durable revocation event; use an observed restart and verify the tombstone. Retired-device Agent route checks remain a separate database authorization boundary. A security reviewer must examine that separation and the SQL/file commit ambiguity before integration.
