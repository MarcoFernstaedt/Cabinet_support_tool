# Office lab device credential renewal

This manual operation renews one already enrolled, approved, active device with its original protected Agent key. It is not fleet renewal or key recovery. No live deployment or device check was performed here.

## Package and prerequisites

The delivered kit contains `office_renewal_operator.py` at its root alongside `office_renewal_preflight.py` and `issue_office_enrollment.py`; the source tree holds these under `tools/`. Include the root-level operator file with the matching server and operator kit as a separate named file. It requires Python 3.10 or later, a trusted TLS certificate for the exact server hostname, and a local private directory for the decision file. It uses only the Python standard library. Do not put a password, access token, refresh token or device key in the command line, environment, chat or file. Run on the service owner workstation or VPS with authorized access, not on the cabinet. The client requires a working masked terminal; if Python cannot control one, it refuses before stdin fallback and sends no login. Retry from a trusted interactive terminal, not a plaintext workaround. The Bearer token and password are never deliberately persisted. The Python process and host still need normal operator protection. Do not enable HTTP wire tracing or proxy credential capture. The server logs and TLS termination are separate acceptance gates.

Confirm the matching server revision, OfficeEnrollment enabled, the original private consumed token journal and matching configured token hashes, trusted server time, protected Agent `.device` journal on the SAME physical device, and an approved active cabinet with nonempty historical heartbeat data. The helper reads the cabinet detail and heartbeat history but approval and local key presence require operator confirmation through the approved cabinet view and the device's protected installation. Never copy or print the key. If missing, stop. Suspected key theft or compromise is not a renewal case: refuse renewal and follow the observed revocation and retirement procedure. A stolen key with the same machine ID works during any valid window.

Create an operator owned private directory: `mkdir -m 700 /path/to/private-renewal`. Use a unique decision file per intended cabinet decision. For a new decision:

`python3 office_renewal_operator.py --origin https://server.example --username SUPERVISOR --cabinet-id CABINET_UUID --machine-id EXACT_MACHINE_ID --state /path/to/private-renewal/decision.json --reason 'specific lab session reason'`

The arguments are nonsecret; the password is entered privately. Check the displayed cabinet UUID, machine ID, actor ID, prior contact and history, then type the exact machine ID and `YES` only after checking approval, the original device journal and absence of suspected compromise. The helper writes the request UUID, normalized reason, actor ID, origin, cabinet and machine identity, prior contact and history metadata in a 0600 file and syncs it BEFORE posting. It refuses an existing file when `--reason` is supplied. Protect and retain this nonsecret attribution file. It is not a substitute for the server journal. A server response alone does not prove contact.

If the response is lost, a 500 occurs or contact is not yet visible, reuse the SAME file and SAME Supervisor account in a fresh process and omit `--reason`:

`python3 office_renewal_operator.py --origin https://server.example --username SUPERVISOR --cabinet-id CABINET_UUID --machine-id EXACT_MACHINE_ID --state /path/to/private-renewal/decision.json`

The helper rejects redirects and non HTTPS origins, checks current user and role, target activity, identity, history, response UUID and UTC expiry, and looks for a newer check in plus the previous heartbeat ID under the same cabinet. If a new contact has not yet been recorded, leave the file intact, allow the Agent its normal retry, and run the same command later. Concurrent retention or equal timestamp heartbeats can prevent automatic history verification; inspect the protected server history manually, not a new grant. The response of an exact retry is the ORIGINAL expiry. The server binds retries to the Supervisor user ID, not the login session. If that user loses authority, stop and reconcile through authorized review rather than substituting another user or UUID.

A mustChangePassword response blocks renewal until the supported password change workflow completes. HTTP 401 requires sign in again as the same user; 403 means authority denied; 409 can mean a missing or retired cabinet, revoked or missing grant, UUID collision or the 30 decision cap. Do not bypass 409 by clearing a journal, restoring an older snapshot, generating a new request ID for an uncertain outcome, or reenrolling an existing identity. An intentional new day requires a NEW file and UUID only after the previous decision and contact are resolved. No indefinite extension is supported.

## Persistence and rollback

Each decision expires 24 hours after the server records it. The original token permits initial enrollment only for its short configured window, and original device authorization expires at its configured time. At most 30 decisions exist per device. Journal replacement is flushed and exclusive, but file and SQL audit are not one atomic transaction: an HTTP 500 can have recorded an active grant while the SQL success audit is absent. An exact retry can fill in the audit if the cabinet and actor remain eligible. The journal remains authoritative for expiry and attribution. Preserve all journal and database history; never initialize an empty journal to fix startup refusal.

Revocation requires removing the matching token from protected server configuration, stopping and restarting the current server to observe that absence, and verifying the durable tombstone BEFORE considering rollback. The current reader replaces the revoked key hash with a random unreachable hash while retaining the token hash, machine identity and renewal history. This also makes the original key unusable to the baseline ce7f349 parent reader that ignores Revoked, even if an old token configuration is accidentally reintroduced. An already tombstoned journal from the earlier renewal revision must be opened by this corrected reader once to shred its stored key hash before any downgrade. Do not put a baseline reader online beforehand. Keep the exact protected journal and token configuration; do not restore a pre revocation snapshot. Backup rollback can undo the tombstone and is outside this guarantee. The older reader's 128 KiB journal ceiling can also refuse a large renewed journal; that refusal is safe and must not be worked around by resetting history.

For an authorized lab rollback, stop the server and back up the database, journal, token manifest and configuration consistently in protected storage. Preserve the post migration journal. Use a compatible rollback build that reads and writes `Renewals`, `Revoked` and `KeyDestroyed` without erasing attribution and retains the Office mode pin. Do not start a pre renewal writer against a journal with renewal history: it ignores renewal fields and a later write can erase them. The baseline reader test proves only refusal of the original key on an unchanged shredded journal, not safe continued operation. Test old key refusal and renewal history retention with the exact candidate rollback build on a disposable copy before any service exposure. If no compatible rollback exists, keep the corrected build offline while recovering it; never reset grants or restore a pre revocation snapshot as a routine workaround. No deployed rollback was performed here.

## Before opening the corrected reader

`Program.cs` loads `office-enrollment.json` optionally. Missing or empty tokens can start Office mode and permanently shred every existing binding. Access refusal is not a startup failure or protection of recoverable hashes. Stop the service first and retain a consistent protected backup of the current database, journal, manifest and all configuration overlays. Verify original file paths, ownership, private directories, trusted clock and exclusive journal ownership. Do not use this helper on a running journal or a live service.

Use the kit root `office_renewal_preflight.py` on the stopped server as the file owner. It reads four absolute private files without mutation: `--manifest` is the reviewed `office-enrollment.json`; `--effective` is a separately prepared JSON snapshot of the actual final `OfficeEnrollment` section after appsettings, manifest, environment and command line precedence; `--inventory` is a reviewed JSON object with `StateFile`, `Tokens` (all known intended token hashes, including previously consumed hashes), and `Revoked` (explicitly approved removals, also listed in `Tokens`); `--journal` is the exact existing consumed journal. Treat the hashes and these files as private configuration metadata; do not print their contents. The snapshot is not created by this tool. An operator must verify its provenance from the exact service launch and overlays, including Office mode pinned independently of the optional manifest; a hand copied or partial snapshot does not prove effective configuration. Avoid unreviewed environment or command line overrides after capture.

`python3 office_renewal_preflight.py --manifest /private/office-enrollment.json --effective /private/effective.json --inventory /private/inventory.json --journal /private/grants.json`

The helper compares exact state path, enabled mode, configured hashes and issuance windows against the effective snapshot, and both configurations against complete inventory and existing journal bindings. It aborts on missing or accidental empty configuration, an unlisted binding or a removal not explicitly in `Revoked`. Deliberate removal needs both manifest and effective snapshot to omit that hash and inventory to include it in `Revoked`. A PASS is only a read-only source check, not an activation permit or a substitute for verifying the running service configuration. On a protected disposable copy, rehearse the corrected reader, compare all grant identity and renewal history and verify only approved removals are shredded. Keep the exact migrated journal. Do not activate if the snapshot cannot be established or the rehearsal differs.

## HP restored-state reinstall, parent review only

Authorized temporary HP Agent removal is not a fresh enrollment. The current installer rejects an existing target and expects an unexpired enrollment input; it cannot re-enroll the same hardware into its existing cabinet. Do not relax those guards, spoof identity or delete server history. Before any removal, review package provenance and a restore-aware procedure. Stop the Agent gracefully, then capture the original private `.device` credential, Agent configuration, pending/operational state and service definition in protected local recovery storage without printing credential material or hashes. The minimal recovery path installs the reviewed binary and original configuration with service start disabled, restores original state and permissions to the original paths before first start, checks original endpoint and hardware-derived machine identity, then starts once. On failure, stop and restore the original service, binary and state without overwriting the preserved recovery copy. Verify authenticated contact, exact cabinet UUID and machine ID, approval/activity and nonempty previous history. This is a procedure for independent review, not an implemented second installer path or an executed HP test. Fresh enrollment acceptance requires a separately authorized fresh identity.

Authentication rejects times before the latest renewal issue timestamp and at or after its expiry. The server still relies on a trustworthy clock: rollback into an earlier valid window can make a formerly expired grant valid again; tests do not prove monotonic time, crash durability or resistance to restored backup snapshots. Native Windows, TLS at a real server, actual same device contact and deployed history readback remain blocked pending authorized acceptance.
