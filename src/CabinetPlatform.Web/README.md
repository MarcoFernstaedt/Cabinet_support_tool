# Local browser sign-in for the Event Viewer preview

## Fictional operator demo (no backend or login)

From this directory run `npm ci && npm test && npm run demo`, then open **http://127.0.0.1:4174/** on the same computer. The demo server is a separate loopback-only, static, allowlisted process; it does not use the password gateway, contact the Cabinet Server/Agent, accept form submissions or expose the existing upstream preview. Do not forward this port or use it with customer data. Stop with Ctrl+C.

Walkthrough: search `Harbor` in the finder, open `Atrium scanner`, inspect site context, switch to `Gallery scanner` using the same-site navigation, then select `All checks`, `Connectivity`, and `Fingerprint`. The latter shows the selected scanner family and three proposed scanner-family definitions. Try `Orchard` to visit a different site and clear or miss a search to see the bounded empty state. Browser back/forward navigates cabinets via URL fragments. Everything displayed is fictional; no diagnosis has run and no pass/fail result exists. `All checks` is a proposed umbrella of individually selectable modules, not an executable endpoint. The actual fingerprint script/fields and native scanner semantics are pending review. This is a visual interaction prototype, **not** production acceptance or a real authenticated, scoped staff workflow. G01–G08 remain blocked.

The existing password-based Node preview below is a separate development gateway; `npm start` still requires its explicit local-server setup and does not become production-ready by running this demo.

This branch uses the Windows Console's staff username and password endpoint, `POST /api/auth/login`. That endpoint is not OAuth. The browser sends the password to this loopback-only gateway. The gateway forwards it over HTTPS to the Cabinet Server, holds the short-lived access token in process memory and gives the browser an opaque, HTTP-only, SameSite=Strict cookie. Every protected request checks `/api/auth/me` again so account or session revocation can close access. The refresh token is discarded. Sign-out removes the local session, and a form token plus Origin check protect the sign-out request.

Run `npm ci` and `npm test`, then set `CABINET_WEB_LOCAL_LOGIN=1` and `CABINET_WEB_UPSTREAM` to the **HTTPS origin of a disposable Cabinet Server test instance bound to 127.0.0.1 or ::1**. Run `npm start` and open `http://127.0.0.1:4173` on the same machine. Do not paste real credentials into source code, command arguments or chat. Do not point this build at a production server, including through a local tunnel or reverse proxy. The loopback-origin check blocks a direct remote upstream but cannot prove that the upstream database holds only synthetic records. Verify its database and test accounts before running it. The preview refuses non-loopback binding, remote upstream URLs and startup without explicit opt-in. The browser connection is plain HTTP over loopback, so do not forward the port or browse from another computer.

## Supervisor enrollment and retirement (synthetic preview)

The Supervisor queue at `/enrollment` pages pending registrations. Its approval and rejection confirmations show the registration, reported hostname and machine ID. Cabinet detail links to `/cabinet/{id}/retire` for a separate retirement confirmation. The gateway accepts only exact GUID routes and bounded form fields, checks the exact browser Origin and the session's random CSRF token on each POST, rechecks active Supervisor status through `/api/auth/me`, and reads the target again before sending a narrow JSON request. It does not send or display enrollment tokens, device keys or browser bearer tokens. Server authorization and its conditional pending-status decision remain authoritative. Refreshing a queue or cabinet before POST is not an atomic precondition; a concurrent decision can still win. On a refused or uncertain outcome, inspect the fresh queue/detail before attempting another confirmation. Retirement disables operational access and retains history; credential erasure on the device is unverified.

Approval takes client, site, department and one of Sync, Satellite or Standalone. The preview requires a nonblank reason and sends it as `approvalReason`; the Server records the trimmed reason in the named Supervisor approval audit. Older clients can omit this optional contract field. Rejection and retirement reasons are transmitted in their exact request contracts. There is no MFA, independent staff-to-cabinet authorization, production ingress protection or live Windows acceptance. Do not use this gateway against real cabinets, credentials or customer data, even via a loopback forward. This preview has no remote control feature.

The display preview at `/cabinet/{id}/display` reads only a saved, bounded `GetDisplayDiagnostics` action for that cabinet, with an action-pinned link so a later collection cannot replace the selected result. OS modes visible to the Agent service are not proof of the active user's effective display state. Scaling, Magnifier and app zoom are explicitly not collected by the service, remain unknown, and earlier saved session-inaccessible results remain readable; this page offers no display correction or remote access. Native Windows service context and browser accessibility are not yet tested.

The storage preview at `/cabinet/{id}/storage` uses a narrow, audited cabinet-bound Server projection of the latest heartbeat disk summary, privacy-limited inventory volume observations and up to 32 retained SMART readings. It does not expose serials, drive letters, models, raw inventory or collector errors. Embedded free-space values belong to an inventory version's first observation, not the later confirmation; the heartbeat's disk verdict can be carried from an older full collection. Each reported serial has an opaque cabinet-bound link to `/cabinet/{id}/storage/trends` for a bounded seven-day window and paged retained SMART observations. Newly accepted readings persist their own Server receipt; earlier readings and daily rollups have unknown receipt. The shown dominant source is not field-level provenance, and a serial does not prove physical-drive continuity. Missing counters and missing drives are unknown rather than healthy, and a retained drive could have been removed. This is only a historical disposable-data preview without staff authorization, native Windows validation or a production Data Protection key ring.

The crash preview at `/cabinet/{id}/crashes` keeps saved Application Error and Event Viewer clues separate from bounded WER machine queue/archive metadata and a separate local Security 4688/4689 process lifecycle observation. Each has an exact cabinet/action-pinned Server projection. The page labels report creation time and incomplete store coverage, not crash time or a matched cause. Process starts and exits carry a timestamp and PID, but no reconstructed lifetime or verified historical audit continuity; an empty result is not proof that no process ran. No WER files, dumps, filenames, signature parameters, report keys, paths, raw Security XML, command lines or native error text are returned to the browser. This synthetic preview is not approved for real data: native Windows service behavior, child-process termination, result retention policy, staff scope and browser accessibility remain unverified.

The default Event Viewer at `/` still displays clearly labelled fictional records for layout testing. From a cabinet detail page, `/cabinet/{id}/events` instead reads the latest saved `RunEventLogView` result for that exact cabinet through a narrow, bounded Server projection. It does not request a new action or blend fictional records with collected results. The network history page at `/cabinet/{id}/network-history` uses a bounded, cabinet-scoped accepted-interval read with observed-time cursor and optional exact target filter. It keeps Agent observation and Server receipt separate, labels retained replies and local probe errors, and does not infer a complete outage timeline or recovery onset from missing rows. Late replay and retention mean pagination is not an immutable snapshot. The read-only incident evidence page at `/incident/{id}/correlation` pins an alert to its accepted interval and directed source/target cabinet identities. It shows server contact, separately timed heartbeat collection/receipt, current topology and any accepted coarse source firewall-profile clue without inferring simultaneity, firewall cause, application sync or measured recovery. It explicitly marks application-port evidence as not collected. The fleet and site health page at `/fleet/health` is a separate local-only overview. It paginates active cabinets and sites, labels contact time separately from the latest heartbeat collection/receipt, distinguishes never-measured and stale measurements from Unknown health, and shows historical sync reachability without assuming firewall causation. Site order is stable by client/site identity rather than incorrectly claiming fleet-wide severity order. Summary and pages are separate reads, not a transactionally consistent snapshot; a mismatch is treated as unavailable rather than as a false count. Fleet-scale PostgreSQL latency and browser accessibility are unverified. The local Fleet finder, cabinet detail, site incident, saved event, crash-clue and process/service pages make bounded read-only server requests with the bearer token held by the gateway, not browser JavaScript. The process page shows an exact cabinet-bound, action-pinned `GetProcessList` projection with only image name, PID and nullable counters; it never exposes executable path or selection identity. It also shows retained service names/states from the current inventory version, with first and last observation times. An unchanged inventory can retain an old PID, so the page does not display or match service PIDs to process rows. Neither process action completion nor service inventory confirmation proves live state or crash-time presence. No process or service controls are exposed. The crash page remains incomplete: it shows saved Application Error and Windows Error Reporting event metadata, separate bounded typed WER report metadata, and unpaired recorded Security process starts and exits, not a diagnosed cause or a verified crash-time process inventory. Links to exact collected events use a cabinet-bound saved action ID, so a newer collection cannot silently replace the selected event; a retained action that is removed returns not found. A missing, pending, failed, partial or truncated event result is labelled rather than shown as an empty success; older records are not substituted when a newer request is pending. The Server policy remains role-wide, not staff-to-cabinet authorization. These are development test surfaces and must use synthetic cabinets only. No annotations, generic API proxy, file access or remote control are exposed. This password-only flow has no MFA and is **not approved for deployment or real support work**. Before making a browser Console available to staff, replace this development-only gateway with the reviewed Entra MFA flow, enforce immutable Cabinet staff mapping and per-cabinet authorization, and test real tenant policy, secure sessions, revocation, auditing, representative fleet performance, Windows Agent-to-Server-to-web transport and native browser accessibility. The separate Entra host has no cabinet data routes. The WPF Console remains the operational UI.
